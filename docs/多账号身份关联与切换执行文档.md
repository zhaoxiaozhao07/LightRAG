# 多账号身份关联与切换执行文档（后端 API MVP）

> **文档定位**：本文是后端 API MVP 的执行约束、数据契约和验收清单，不表示本文写入时相关功能已经实现。当前代码、现有 JWT 和现有账号数据仍以仓库实现为准；实施时必须先加测试，再逐阶段打开功能开关。
>
> **核心定义**：`person` 是自然人身份；`enterprise_users` 中的一行是一个业务账号（下文简称"账号"）。自然人凭据是跨账号切换的信任根，账号的 `password_hash` 只保留用于 legacy 账号登录。一个自然人可以关联多个账号，但一个账号在任一时刻最多只能有一个有效的自然人关联。
>
> **协议裁决者**：本项目为受控内网、纯后端部署。平台 `super_admin` 是本 MVP 的可信身份裁决者：只有 super admin 经线下核验后签发的一次性 enrollment grant 才能建立自然人身份。tenant_admin 只能在本 tenant 内管理账号/tenant membership/KB ACL，无权裁决跨 tenant 的自然人身份；tenant_admin 可为**本租户普通成员账号**提议 pending link（部门管理员为本部门成员发起绑定），但目标为 tenant admin/owner 账号的提议、grant 签发、解绑与 person 停用/启用仍仅限 super admin，且任何提议都必须由 person 本人用自然人密码确认后才激活。

## 1. 当前项目事实

以下事实来自当前仓库的实现和接口契约；行号会随代码变更移动，引用以文件内容为准。

### 1.1 `lightrag/api/metadata_store.py`

- SQLite metadata store 已有 `enterprise_users` 表及 `EnterpriseUserRecord`，账号至少包含 `id`、唯一 `username`、`password_hash`、`system_role`、`status`、`tenant_id`、能力位、`token_version`、metadata 和时间字段。
- `enterprise_tenant_memberships` 以 `(tenant_id, user_id)` 为主键，并通过修复逻辑和 `user_id` 唯一索引保持一个账号只有一个 canonical tenant membership；现有 `enterprise_users.tenant_id` 与该 membership 需要保持一致。
- 个人查询设置、chat project/session/message、chat memory 等记录都带有 `user_id`；KB ACL 也以账号 `user_id` 作为主体键。不能把自然人 ID 直接替换成这些记录中的 `user_id`。
- SQLite schema 初始化使用 `CREATE TABLE/INDEX IF NOT EXISTS`，并包含既有数据修复逻辑。新增 person 表应沿用同一初始化/事务路径，不改写既有账号行。
- 现有审计记录 `enterprise_audit_events` 已支持 `event_type`、`actor_user_id`、`actor_tenant_id`、`target_type`、`target_id`、metadata 和创建时间，MVP 优先复用该审计面。

### 1.2 `lightrag/api/enterprise_auth.py`

- `EnterpriseUserRecord` 是当前企业账号的认证和授权数据来源；现有 `authenticate()` 按用户名读取 active 账号并校验账号密码。
- `Principal` 的核心身份字段是 `user_id`，同时携带 `username`、`system_role`、`tenant_id`、`tenant_roles`、能力位、`token_version` 和 `auth_method`。`Principal.user_id` 当前表示账号 ID，不是自然人 ID。
- 现有 token 解析会重新读取账号，校验账号仍为 active，并比较 token 中的 `token_version`；版本不一致时令 token 失效。现有全设备登出、禁用账号、重置账号密码等操作会递增该版本。
- 现有密码辅助逻辑（`lightrag/api/passwords.py`）兼容历史账号密码格式，包含明文回退。person credential 不得复用该路径，必须严格保存和校验 bcrypt 值。
- 现有角色包括 `super_admin`、`user` 以及 tenant/KB 角色。person 机制只负责建立信任和选择账号，不自行产生新的 RBAC 角色。
- `tenant_admin` 可以重置本 tenant 成员的账号密码。因此**账号密码不能证明自然人身份**，只能证明账号控制权；tenant_admin 在内网 MVP 中被默认为"可以完全冒充本 tenant 成员账号"的可信主体，但没有跨 tenant 身份裁决权。

### 1.3 `lightrag/api/routers/enterprise_routes.py`

- 企业路由通过 combined auth 获取当前 principal。`GET /auth/me` 允许 service API key（此时返回 `user=null`）；`PATCH /auth/me` 和 `POST /auth/logout` 才要求 interactive JWT（service key 返回 403）。
- 当前已有企业注册、账号管理、tenant membership、KB ACL、审计等路由；管理员路由有 super admin 边界，tenant 管理员不能借此跨 tenant 管理账号。
- 现有 tenant 审计查询按 `actor_tenant_id` 返回完整事件 metadata，并对 target user 补全 username。person 身份事件若直接写入会跨 tenant 泄露，必须特殊处理（见第 7 节）。
- `/auth/person/*` 与 `/admin/persons/*` 路由现已实现于 `lightrag/api/routers/person_routes.py`（工厂 `create_person_routes()`，仅在 `LIGHTRAG_PERSON_AUTH_ENABLED=true` 时挂载）；对外契约以 `docs/API接口.md` 10.6 节为准。

### 1.4 `lightrag/api/auth.py` / `utils_api.py`

- 现有 `AuthHandler` 只使用一个 `TOKEN_SECRET`，`validate_token()` 只校验签名、算法和过期，最终只返回 `sub/role/metadata/exp`；**不检查** `sid/person_id/session_epoch/typ/iss/aud/jti`。
- 企业 middleware 随后把 metadata 交给 `principal_from_token_info()`，只检查账号和 `token_version`。
- 这意味着：如果 v2 person token 仍由旧 `TOKEN_SECRET` 签名，回滚到旧 binary 或关闭功能开关后，旧 validator 会忽略 person/session claims，把已 logout/已解绑/已过期 epoch 的 v2 token 当作普通账号 JWT 接受。**因此 v2 person token 必须使用独立签名密钥和确定性分派（见第 6 节）。**

### 1.5 `lightrag/api/postgres_metadata_store.py`

- PostgreSQL metadata store 在初始化时使用事务级 advisory lock，再以原子事务执行 schema 初始化和修复；生产控制面使用 PostgreSQL。
- PostgreSQL 现有企业表使用显式列配合 `data_json JSONB`，账号通过账号 ID 关联。
- 现有 membership 的单 tenant 约束和索引在 schema repair 阶段建立；person 新表必须在同一初始化锁和事务中创建，不能只在单进程启动时补表。

### 1.6 `docs/API接口.md`

- 当前 `POST /login` 在企业模式下使用企业用户表，返回包含 `user_id`、`system_role`、`token_version` 等 metadata 的 JWT；该接口是现有账号登录契约。
- 当前 `/auth/logout` 是账号维度的全设备登出，会递增账号 `token_version`。它与本文新增的 person session 登出不是同一个语义，旧接口必须保持不变。
- 现有文档明确企业模式为内网部署，SSO/OIDC/SAML 不在当前认证范围。

### 1.7 由事实得到的实施边界

本阶段只在现有企业认证之上增加一个"自然人凭据 → 已显式授权账号 → 普通账号 JWT"的薄层。不得借此重构 `enterprise_users`、改变 `Principal.user_id`、合并账号数据，或把尚未实现的 person API 写成当前 API 契约。

## 2. 范围与非目标

### 2.1 本阶段范围

- 纯后端：新增 person/credential/link/session/enrollment-grant 持久化、SQLite/PostgreSQL 幂等迁移、FastAPI 路由、JWT 校验、审计和自动化测试。
- 部署假设为受控内网。密码、JWT 和 session 查询不依赖外网服务；需要的 bcrypt 在现有 Python 运行时内完成。
- 通过一次性 enrollment grant 建立自然人身份；通过 person credential 登录后，用户只能在有效 link 集合中选择一个账号，并获得该账号语义的普通账号 access JWT。
- 新部门账号由 `super_admin` 或**目标账号所属租户的 tenant_admin**（仅限普通成员账号）创建为 **pending link**，再由该 person 本人用自然人密码确认激活；pending link 不出现在可切换集合。
- 自然人改密、停用/启用、单会话登出、全设备登出均在本阶段实现。

### 2.2 明确非目标

- **不接外网 IdP/SSO**：不做 OIDC、SAML、LDAP、OAuth 社交登录、自动目录同步或任何外部身份映射。
- **不做前端**：不修改 Web UI、登录页、路由跳转、状态管理或视觉交互；客户端只按本文的后端契约调用 API。
- **不做 impersonation**：不增加"以某账号身份执行"的管理员代入能力，不允许通过 header、query 参数或隐藏字段伪造 `user_id`。
- 不按 email、姓名、手机号、用户名相似度或模糊匹配自动关联；本阶段没有"发现后自动绑定"。
- 不迁移、合并、复制或重写不同账号的 KB、chat、job、memory、ACL、审计数据。
- 不把普通账号密码改造成 person 密码，也不实现"尝试该自然人所有账号密码"的登录策略。
- 不承诺 refresh token、跨设备共享 token、设备/会话列表界面、密码找回、外部邮件/短信通知；如后续需要，另立设计和验收。**完整邀请通知系统可以延期，但 admin 提议 → person 本人确认激活这一最小确认动作不可延期。**

## 3. 不变量

下列规则是实现和回归测试必须同时满足的硬约束：

| 编号 | 不变量 | 执行要求 |
|---|---|---|
| I-1 | `enterprise_users` 仍是账号真源 | `account_id` 永远等于现有 `enterprise_users.id`；person 表不复制账号权限字段，也不取代账号密码/状态。 |
| I-2 | 单 tenant membership | 每个账号继续最多一个 canonical tenant；`enterprise_users.tenant_id`、`enterprise_tenant_memberships` 和现有 CAS/repair 规则不因 person link 改变。 |
| I-3 | `Principal.user_id` 是账号 ID | 新 token 解析后仍生成普通 `Principal`，`user_id=当前选中的 enterprise_users.id`；`person_id` 只能作为附加认证 metadata，放 `request.state.person_session`，不进 `Principal.metadata`。 |
| I-4 | 业务数据按账号隔离 | KB、chat project/session/message、job、memory、直接 user ACL、个人设置和审计中的账号主体仍按 `user_id`/账号语义过滤；切换不产生数据并集。 |
| I-5 | link 不是授权替代物 | link 只证明该 person 可以选择该账号；账号原有 status、tenant membership、能力位、KB ACL 和 RBAC 仍必须独立校验。 |
| I-6 | person credential 是跨账号信任根 | 只有有效 person credential/session 加上有效 link 才能切换；普通账号 `password_hash` 只支持该账号的 legacy `/login`，不能跨账号使用。首次 enrollment 必须由 super admin 签发的 enrollment grant 建立，不接受"账号 JWT + 账号密码"作为自然人身份证明。 |
| I-7 | 旧认证可继续工作 | 没有 person claims 的旧 `/login` JWT 仍按原有签名密钥、过期时间、`user_id` 和 `token_version` 规则工作；旧客户端不需要感知 person。v2 person token 用独立密钥签名，旧 validator 因无该密钥无法验证。 |
| I-8 | 失效及时生效 | 每次使用新 person token 都校验账号、person、session、epoch 和 link；不能用不一致的长缓存绕过 logout、解绑、禁用或密码重置。 |
| I-9 | 绑定必须显式且需本人确认 | enrollment 只接受 super admin 签发的一次性 grant；其它/新部门账号由 super admin（任意非 super-admin 目标）或目标所属租户的 tenant admin（仅限本租户普通成员目标）创建 pending link，必须由该 person 用有效 session + 当前自然人密码确认后才激活。激活新 link 必须递增 `auth_epoch`、撤销全部旧 session。不能由 email/姓名/用户名自动推断，也不能由任何 admin 直接产生 active link。 |
| I-10 | 一个账号不共享自然人信任 | 同一账号最多一个 active person link；并发绑定必须由数据库唯一约束裁决，不能出现两个 person 都能切换到同一账号的竞态状态。 |
| I-11 | 双校验分层 | session-control 校验（accounts/switch/logout/change-password/confirm link）不要求旧 active account 仍 active 或 token_version 一致；account-access 校验（业务 API）额外要求账号 active、token_version、link、canonical membership。当前账号被 disable/reset/delete 后，用户仍能切换或退出。 |
| I-12 | 审计同事务且平台级隔离 | 安全状态变更与审计写入必须同一 `_write()` 事务；person 身份事件 `actor_tenant_id=None`，只由 super admin 审计接口可见完整跨 tenant metadata，tenant 审计不得返回 person 事件或跨 tenant 目标信息。 |

## 4. 数据模型与幂等迁移

以下是建议的逻辑模型和表名。表名使用 `enterprise_` 前缀；这是待实现的 schema，不代表当前数据库已经存在。

### 4.1 `enterprise_persons`（person）

| 字段 | 要求 |
|---|---|
| `id` | `TEXT PRIMARY KEY`，服务端生成不透明 ID，例如 `per_<hex>`；不得把 email/姓名作为主键。 |
| `status` | `active` / `disabled`；禁止用删除来代替停用。 |
| `auth_epoch` | 整数，初始为 `1`；person 密码变更、停用、logout-all、新 link 激活等全局撤销操作递增。 |
| `metadata_json`（SQLite）/`data_json`（PostgreSQL） | 仅存非安全显示 metadata；不存明文密码、raw JWT 或可恢复的 token。 |
| `person_number` | 可空 `TEXT`，**工号**（现实存在的员工编号）：登录时可替代不透明 `person_id` 的精确唯一键。非空值上建部分唯一索引 `uq_enterprise_persons_person_number`（`WHERE person_number IS NOT NULL`）。签发 grant 时指定（enroll 落库）或 `PATCH /admin/persons/{person_id}` 补录/改绑/清除。 |
| `created_at`、`updated_at` | UTC 时间，非空。 |

MVP 不增加 email、手机号或可用于自动匹配的外部身份字段。若需要显示名，只能是显式设置的展示属性，不能作为绑定条件。工号是**显式绑定的精确唯一键**（等价于第二个主键式标识），不是模糊匹配字段，不违背本条。

### 4.2 `enterprise_person_credentials`（person credential）

| 字段 | 要求 |
|---|---|
| `id` | credential ID，主键。 |
| `person_id` | 非空外键，指向 `enterprise_persons.id`。 |
| `credential_type` | MVP 固定为 `password`。 |
| `algorithm` | MVP 固定为 `bcrypt`。 |
| `password_hash` | 保存严格 bcrypt 结果。实现采用 **SHA-256 预哈希再 bcrypt**，存储表示为 `{bcrypt-sha256}$2b$...`（校验时兼容纯 `{bcrypt}` 前缀）；严格禁止明文回退，禁止调用 `passwords.py` 的 legacy 验证路径。 |
| `status` | `active` / `revoked`。 |
| `failed_count`、`locked_until`、`last_used_at` | 用于跨 worker 的登录失败控制和运维观察；失败计数更新必须原子化。 |
| `created_at`、`updated_at` | UTC 时间，非空。 |

约束：`UNIQUE(person_id, credential_type)`，MVP 每个 person 只有一个 active password credential；密码轮换更新该行并递增 `enterprise_persons.auth_epoch`、撤销全部 session。bcrypt cost 复用现有运行环境基线，不在请求中降低 cost。bcrypt 72-byte 限制：对全部输入先做固定 SHA-256 预哈希再 bcrypt（`{bcrypt-sha256}` 表示）；密码校验对不存在的 person 必须执行 dummy bcrypt 以平滑时序。**失败计数在 SQL 侧原子自增**（`failed_count = failed_count + 1`），login/confirm-link/change-password 三个自然人密码再认证入口共用同一计数与锁定，失败写 `person_login_failed`（达阈值另写 `person_login_locked`）审计且不伪造 actor。

### 4.3 `enterprise_person_enrollment_grants`（一次性注册凭据）

| 字段 | 要求 |
|---|---|
| `id` | grant ID，主键，例如 `pgrant_<hex>`。 |
| `account_id` | 非空外键，绑定精确的目标账号 `enterprise_users.id`；enroll 成功后该账号成为初始 active link。 |
| `token_hash` | grant token 的单向 hash；**只存 hash，不存明文**。明文 token 只在创建时返回一次。 |
| `status` | `active` / `consumed` / `revoked` / `expired`。 |
| `created_by` | 签发该 grant 的 super admin 账号 ID。 |
| `consumed_by_person` | 消费后写入所建 person ID。 |
| `expires_at` | 短有效期（建议 15 分钟）。 |
| `person_number` | 可空 `TEXT`：签发时指定的工号，enroll 消费时落到新建 person 上；persons 表的唯一索引在消费时终裁（冲突→事务回滚，grant 保持 active）。 |
| `created_at`、`updated_at`、`consumed_at` | UTC 时间。 |

约束：`UNIQUE(account_id)` 上对 `status='active'` 建部分唯一索引——一个账号同一时刻最多一个未消费的 active grant。只有 `super_admin` interactive JWT 可创建/撤销 grant；tenant_admin 无权创建。grant 在 enroll 事务中被原子消费（`active→consumed`），过期/已消费/已撤销的 grant 不可再用。

### 4.4 `enterprise_person_account_links`（person-account link）

| 字段 | 要求 |
|---|---|
| `id` | link ID，主键。 |
| `person_id` | 非空外键，指向 person。 |
| `account_id` | 非空外键，指向 `enterprise_users.id`，`ON DELETE CASCADE`（账号删除时 link 行级联删除，绑定历史由 append-only audit 保留）。 |
| `status` | `pending` / `active` / `revoked`。 |
| `bound_by`、`bound_at` | pending 由 super admin 提议时记录；active 由 person 确认或 enrollment 时记录。 |
| `confirmed_by_person_at` | person 确认激活的时间。 |
| `revoked_by`、`revoked_at`、`reason` | 解绑和异常处置的审计信息。 |
| `created_at`、`updated_at` | UTC 时间，非空。 |

约束和索引：

1. `UNIQUE(person_id, account_id)`，同一 pair 重新提议/激活时更新原行，不插入重复历史行。
2. 对 `status='active'` 建立 `UNIQUE(account_id)` 的部分唯一索引；一个账号不能被两个 person 同时有效关联。**pending link 不受该唯一约束保护成"可切换"，但 active 化时由部分唯一索引裁决并发。**
3. 建立 `(person_id, status)`、`(account_id, status)` 索引；所有读取只取 active link，并再次检查账号状态。
4. 目标为 `system_role=super_admin` 的账号默认禁止绑定，除非另行批准安全设计；MVP 不借 person 机制扩大 super admin 面。该禁令在**每个环节**复查：grant 签发、enroll 消费、propose、confirm、switch 与 account-access 均校验 `system_role`——账号在绑定后被提升为 super_admin 时，person token 对它立即不可达。
5. 新 link 激活（pending→active 或 enroll 首次 active）必须递增 `enterprise_persons.auth_epoch` 并撤销该 person 全部旧 session，要求重新 person login。

### 4.5 `enterprise_person_login_sessions`（login session）

| 字段 | 要求 |
|---|---|
| `id` | session ID，例如 `psess_<hex>`，主键。 |
| `person_id` | 非空外键，指向 person。 |
| `active_account_id` | 当前选中的 `enterprise_users.id`；允许 `NULL`（账号被删除时），`ON DELETE SET NULL`；**nullable**。 |
| `status` | `active` / `revoked` / `expired`。 |
| `person_epoch` | 签发时复制 person 的 `auth_epoch`。 |
| `session_epoch` | 每次 switch 或当前 session logout 递增；用于拒绝旧 token。 |
| `account_token_version` | 签发/切换时快照当前 `enterprise_users.token_version`；account-access 校验时比较 `account.token_version == session.account_token_version`，不一致 → 401。账号 reset password 会递增账号 token_version 但不改 status，故 account-access token 立即失效；session-control 不比较（满足 reset 后仍可 list/switch/logout）。 |
| `absolute_expires_at` | session 绝对过期时间；switch 不延长。 |
| `created_at`、`last_seen_at`、`revoked_at` | UTC 时间。 |

- MVP 允许同一 person 多设备多 session；不提供 refresh token。
- **不设 `token_hash` 字段**。身份由 session `id` + 签名中的 `session_epoch` 共同确定；JWT top-level `jti` 仅用于唯一标识/审计，不参与 session 验证。
- 约束：`token.exp <= session.absolute_expires_at`；switch 签发的新 token 沿用原 session 的 absolute expiry，不延长。
- 每次请求必须同时满足：session active 且未过期、token 的 `person_epoch` 与 `session_epoch` 与数据库一致、person active、`active_account_id` 与 token `user_id` 一致（account-access 类）或 session 仍可识别 person（session-control 类）。
- 切换成功后签发新 token（`session_epoch` 递增），旧 token 因 epoch 不一致立即失效。

### 4.6 SQLite/PostgreSQL 幂等迁移要求

- **不修改既有核心表结构**：不向 `enterprise_users` 填 person ID，不重命名 `user_id`，不把现有数据复制到 person 表作为"自动迁移"。
- **SQLite**：在现有 metadata schema 初始化事务中加入五张新表，使用 `CREATE TABLE IF NOT EXISTS`、`CREATE INDEX IF NOT EXISTS` 和 `CREATE UNIQUE INDEX IF NOT EXISTS`；开启外键检查。部分唯一索引示意：
  ```sql
  CREATE UNIQUE INDEX IF NOT EXISTS uq_person_account_active
  ON enterprise_person_account_links(account_id)
  WHERE status = 'active';
  ```
- **PostgreSQL**：在 `PostgresMetadataStore.initialize()` 已有 advisory lock 的事务中创建五张表和索引，使用 `IF NOT EXISTS`、明确的 `CHECK/UNIQUE/FOREIGN KEY`，并用 `ON CONFLICT` 处理 schema version/幂等写入。部分唯一索引使用同等的 `WHERE status = 'active'` 条件。
- 新表创建、索引创建、schema version 记录和必要的修复必须可重复执行；首次启动、重复启动和多个 worker 并发启动都不能产生重复表、重复索引或半迁移状态。
- 迁移前先备份数据库并检查新表中的 active link 冲突；若发现冲突或外键孤儿，迁移应失败并回滚，不能静默选择 person 或账号。
- 初始数据只通过 enrollment grant / 管理员 pending link 产生。不得以 email、姓名、手机号、username、大小写模糊匹配或相似度回填 link。
- 账号删除、停用和 tenant 变更的现有事务必须在提交前处理关联 link/session；两条账号删除路径（`delete_enterprise_user()` 与 `delete_enterprise_user_with_memory()`）都必须接入。FK 策略见 4.4/4.5。

## 5. MVP API 草案

> 下列路径是待实现的 API 草案。除现有 `/login`、`/auth/logout` 等兼容接口外，未实现前不得在部署说明中宣称可调用。所有新端点默认受建议的 `LIGHTRAG_PERSON_AUTH_ENABLED=false` 开关保护；该配置名本身也是待实现配置。

### 5.1 通用约定

- JSON 请求使用 `Content-Type: application/json`。需要 person session 的端点使用 `Authorization: Bearer <person-access-jwt>`（独立签名，见第 6 节）；service/scoped API key 和普通账号 legacy JWT 都不可代替 person session。
- token 响应统一包含 `access_token`、`token_type: "bearer"`、`expires_in`、`person`、`active_account`、`session`。新 token 的业务身份仍是 `active_account`。`expires_in` 为实际剩余有效期：access TTL 与 session 绝对过期剩余时间取较小值（与签发时对 `exp` 的 min() 截断一致）。
- 成功返回的 `account` 对象只包含 `account_id`、`username`、`status`、`system_role`、`tenant_id` 等非秘密字段，不返回 `password_hash`、完整 metadata、raw token 或可重放秘密。
- 错误外层沿用项目 HTTP 错误处理，逻辑错误码必须稳定。密码校验失败、person 不存在、credential 不存在和账号选择不合法不得泄露不必要的账号发现信息；登录失败使用统一错误文本并限流。

### 5.2 超级管理员签发/撤销 enrollment grant

#### `POST /admin/persons/enrollment-grants`

**请求**（仅 active `super_admin` interactive JWT）：

```json
{"account_id": "usr_dept_a", "ttl_seconds": 900, "person_number": "E-1001", "reason": "线下核验后为张三建立自然人身份"}
```

`account_id` 必须是存量的精确账号 ID；目标必须是存在的非 super-admin 账号。`person_number`（工号）可选：enroll 消费时落到新建 person 上；签发时对已绑定工号 fail-fast 查重（`409 person_number_conflict`）。

**成功**：`201 Created`，明文 grant token 只返回一次，服务端只存 hash。

```json
{
  "grant_id": "pgrant_...",
  "grant_token": "<one-time-secret>",
  "account_id": "usr_dept_a",
  "expires_at": "2026-07-30T12:15:00Z",
  "person_number": "E-1001"
}
```

**主要错误**：`400 cannot_bind_super_admin`、`404 account_not_found`、`409 active_grant_exists`、`409 person_number_conflict`、`403 super_admin_required`。

#### `DELETE /admin/persons/enrollment-grants/{grant_id}`

撤销未消费的 grant。幂等：已 revoked/consumed/expired 返回 `200` 并标记当前状态。

#### `GET /admin/persons/enrollment-grants`

列出已签发的 grant（仅 active `super_admin` interactive JWT）。响应**永不**包含明文 token 或 `token_hash`；每项含 `grant_id/account_id/status/expired/created_by/consumed_by_person/expires_at/created_at/updated_at/consumed_at`，其中 `expired` 为时间判定（`expires_at` 已过）。可选 `?account_id=` 与 `?status=active|consumed|revoked` 过滤（status 非法值 `400 validation_error`），按 `created_at` 倒序。

### 5.3 `POST /auth/person/enroll`

**用途**：使用一次性 enrollment grant 创建 person，把 grant 绑定的账号作为第一个 active link，并签发首个 person session。

**请求**（公开入口，受功能开关、bcrypt、按客户端地址限流保护——`LIGHTRAG_PERSON_ENROLL_MAX_ATTEMPTS`/`WINDOW_SECONDS`/`LOCKOUT_SECONDS`，无效 grant 尝试计数，超阈值返回 `429 too_many_attempts`）：

```json
{"grant_token": "<one-time-secret>", "person_password": "自然人密码"}
```

**事务语义**：在单个 aggregate store `_write()` 事务中完成——校验 grant（active、未过期、绑定精确 account_id）、消费 grant（`active→consumed`）、创建 person、创建严格 bcrypt credential、创建 active link、创建首个 session、写审计。任一步失败整体回滚。

**成功**：`201 Created`，返回 person token 响应。person password 只写入严格 bcrypt hash。

**主要错误**：
- `400 validation_error` / `person_password_weak`：字段缺失、超长、空白或不满足密码策略。
- `401 invalid_grant`：grant 不存在、已消费、已撤销或已过期，统一返回，不区分原因。
- `403 account_not_active` / `cannot_bind_super_admin`：目标账号 disabled/pending 或为 super admin。
- `409 account_already_linked`：目标账号已有 active person link（active link 部分唯一索引冲突）。
- `429 too_many_attempts`：enroll 触发限流或锁定。

**安全声明**：enrollment 信任根独立于 tenant_admin 可重置的账号密码。仅当 super admin 签发 grant 时才建立 person；tenant_admin 无法伪造 grant，也无法仅凭账号密码冒充未 enroll 用户建立 person。

### 5.4 `POST /auth/person/login`

**用途**：使用 person credential 登录，并落地一个已经显式关联且 active 的账号。

**请求**（`person_id` 与 `person_number` 二选一）：

```json
{"person_id": "per_...", "person_password": "自然人密码", "account_id": "usr_dept_a"}
{"person_number": "E-1001", "person_password": "自然人密码"}
```

身份标识是**精确唯一键**匹配：不透明 `person_id`，或已绑定的唯一工号 `person_number`；两个都传或都不传返回 `400 validation_error`（在任何查找之前判定，不构成存在性 oracle）。不接受 email/姓名/用户名推断。`account_id` 可选：单 active link 直接登录；多 active link 时自动落地**最近使用**的可用账号（最新 session 的 `active_account_id`，跳过 disabled/super-admin 候选，兜底最早绑定），登录后可 accounts+switch 换账号。

**成功**：`200 OK`，返回 person token 响应。token 的 `user_id` 是落地账号 ID。

**主要错误**：
- `400 validation_error`：身份标识不是恰好一个。
- `401 invalid_person_credentials`：person/工号、密码或 credential 不匹配，统一返回，不区分具体原因；不存在的 person 执行 dummy bcrypt。
- `403 person_disabled` / `account_not_active`：person 或目标账号不可用。
- `404 account_not_linked`：指定账号不是该 person 的 active link；不得尝试其它账号密码。
- `429 too_many_attempts`：失败次数达到保护阈值，带 `Retry-After`。

（历史：多 active link 未传 `account_id` 曾返回 `409 account_selection_required`，已改为自动选择。）

### 5.5 `GET /auth/person/accounts`

**用途**：列出当前 person 可选择的账号，供切换前确认。

**权限**：**person session-control**（见 5.10）；不要求当前 active account 仍 active。旧 `/login` JWT、API key、service key 返回 `403 person_session_required`。该端点只返回该 person 的 active link 对应账号；当前账号若已被禁用，可在此显示为 disabled 以便切换到其它 active 账号，但不能借此访问业务数据。

**成功**：`200 OK`。

```json
{
  "person": {"person_id": "per_...", "status": "active"},
  "active_account_id": "usr_dept_a",
  "accounts": [
    {"account_id": "usr_dept_a", "username": "alice_finance", "status": "active", "tenant_id": "tenant_finance", "system_role": "user"},
    {"account_id": "usr_dept_b", "username": "alice_legal", "status": "active", "tenant_id": "tenant_legal", "system_role": "user"}
  ]
}
```

### 5.6 `POST /auth/person/switch`

**用途**：在当前 person 的 active link 集合内切换账号，并签发新的账号作用域 JWT。

**请求**：

```json
{"account_id": "usr_dept_b"}
```

**权限**：person session-control。目标账号必须是该 person 的 active link、账号 active、tenant/RBAC 数据本身有效。无需输入目标账号密码，也不允许把目标账号密码作为切换凭据。

**事务语义**：在 aggregate store `_write()` 事务中——锁定 session 和 link，确认 person/session epoch 未变化，更新 `active_account_id`，递增 `session_epoch`，写审计，签发新 token。旧 token 必须立即因 epoch 不一致失败；切换不迁移或合并任何业务数据。新 token `exp` 不超过 session absolute expiry。

**主要错误**：
- `401 person_session_invalid`：签名、过期、session 状态或 epoch 不合法。
- `403 person_disabled` / `account_not_active`：person 或目标账号不可用。
- `404 account_not_linked`：目标账号没有该 person 的 active link。
- `409 session_epoch_conflict`：并发切换/登出导致 CAS 失败。

### 5.7 `POST /auth/person/logout` / `POST /auth/person/logout-all`

**`/logout`**：仅撤销当前 person login session（person session-control）。事务中标记 session 为 `revoked`，同一 token 后续请求返回 `401`。不改变其它 session，也不改变现有 `/auth/logout` 的账号维度语义。

```json
{"status": "logged_out", "session_id": "psess_..."}
```

**`/logout-all`**：撤销该 person 的全部 session。事务中递增 `enterprise_persons.auth_epoch` 并撤销所有 active session；当前和其它设备的 person token 后续均返回 `401`。账号本身的 legacy `/login` token 不因 person logout-all 被改写。

```json
{"status": "logged_out_all", "revoked_sessions": 2}
```

### 5.8 `POST /auth/person/change-password`

**用途**：在已知当前 person 密码的条件下轮换自然人凭据。

**请求**（person session-control）：

```json
{"current_person_password": "旧密码", "new_person_password": "新密码"}
```

**事务语义**：校验当前密码；写入新严格 bcrypt；递增 `person.auth_epoch`；撤销该 person 全部 session；写审计。最简单语义是要求重新登录（本端点不返回新 token）。

**主要错误**：`401 invalid_current_password`、`400 person_password_weak`、`429 too_many_attempts`。

### 5.9 admin 提议/确认/解绑 link + person 停用启用

#### `POST /admin/persons/{person_id}/accounts/{account_id}` （提议 pending link）

**请求**（active `super_admin` 或**目标账号所属租户的 tenant admin** interactive JWT/person JWT）：

```json
{"reason": "新部门账号显式绑定，待本人确认"}
```

**权限矩阵**：super admin 可对任意存量非 super-admin 账号提议；tenant admin（含 owner）只能对**本租户普通成员账号**提议——目标为 tenant admin/owner 账号时返回 `403 super_admin_required`，目标在其它租户或无租户时返回 `404 account_not_found`（防跨租户账号探测），调用者既非 super admin 又非任何租户管理员时返回 `403 admin_required`。

无论谁提议，都只能创建 `status='pending'` 的 link，**不能直接产生 active link**。`person_id`、`account_id` 必须精确 ID。目标必须是存在的非 super-admin 账号。

**成功**：`201 Created`（或幂等返回已有 pending），返回 pending link 摘要（`bound_by` 为提议者账号 ID）；不替 person 签发 token。对已 active 的同一 pair 重复提议返回 `409 link_state_conflict`。

#### `GET /auth/person/links` （person 查看本人全部 link）

**请求**（person session-control）：列出本人**全部** link（`pending`/`active`/`revoked`），可选 `?status=` 过滤（非法值 `400 validation_error`）。与 5.5 的 accounts（仅 active、可切换集合）互补：本端点的核心用途是看到**等待本人 confirm 的 pending link**。每项附带非秘密账号摘要（`account_id/username/status/system_role/tenant_id`；账号行已删除时为 `null`）。走 session-control 路径，当前账号被 disable/reset 后仍可查看。响应：`{"person_id": ..., "links": [{"link": {...}, "account": {...}}], "total": n}`。

#### `POST /auth/person/links/{account_id}:confirm` （person 本人确认激活）

**请求**（person session-control + 当前自然人密码二次确认）：

```json
{"person_password": "自然人密码"}
```

**事务语义**：校验密码；pending→active（由 `active` 部分唯一索引裁决并发）；递增 `person.auth_epoch`；撤销该 person 全部旧 session；写审计。激活后旧 person session 立即失效，必须重新 person login 才能使用新账号。

**主要错误**：`401 invalid_person_password`、`404 link_not_found`（无 pending link）、`409 link_state_conflict`（已被另一 person 抢占 active 或状态已变）、`403 cannot_bind_super_admin`。

#### `DELETE /admin/persons/{person_id}/accounts/{account_id}` （解绑）

**权限**：仅 `super_admin` interactive JWT。

**事务语义**：link `active→revoked`；以该账号为 `active_account_id` 的 person session 同事务撤销或置空；不删除 `enterprise_users`、tenant、KB、chat、job、ACL 或审计数据；写审计。

**成功**：

```json
{"status": "unlinked", "person_id": "per_...", "account_id": "usr_dept_b", "revoked_sessions": 1}
```

**注意**：解绑不是禁用账号，因此旧 legacy 账号 JWT 原则上仍有效（除非同时递增账号 `token_version`）。要彻底阻止对账号的访问应 disable 账号或 unlink。

#### `POST /admin/persons/{person_id}:disable` / `:enable` （person 停用/启用）

**权限**：仅 `super_admin` interactive JWT。`disable` 递增 `auth_epoch`、撤销全部 session、不隐式禁用全部业务账号（业务账号由现有账号管理面独立控制）。`enable` 恢复 person active，不发 token。

#### `GET /admin/persons` （自然人列表）

**权限**：仅 active `super_admin` interactive JWT。每个条目为 person 记录（`id/status/auth_epoch/metadata/person_number/created_at/updated_at`）加 `links` 数组（该 person **全部**状态的 link），可选 `?status=active|disabled` 过滤（非法值 `400 validation_error`）。响应：`{"persons": [...], "total": n}`。只读，不写审计。

#### `PATCH /admin/persons/{person_id}` （工号绑定/补录）

**权限**：仅 active `super_admin` interactive JWT。请求体 `{"person_number": "E-1001"}` 绑定/改绑；`null` 或空串清除。工号唯一（部分唯一索引终裁，冲突 `409 person_number_conflict`）；超长（>64 字符）`400 validation_error`；person 不存在 `404 person_not_found`。绑定后 `person_id` 与工号均可登录；同事务写 `person_number_set` 审计。响应：`{"person": {...}}`。

### 5.10 两类 dependency

实现必须提供两个 FastAPI dependency：

1. **`person_session_control`**：用于 accounts、switch、logout、logout-all、change-password、confirm link。校验——v2 签名/kid/typ/iss/aud、person active、session active/expiry、`person_epoch`/`session_epoch` 一致。**不要求旧 active account 仍 active，也不要求账号 `token_version` 未变化。** 运行时设 `request.state.person_session`。
2. **`person_account_access`**：用于所有现有业务 API。在 session-control 基础上额外校验——当前账号 active、账号非 super_admin、账号 `token_version` 一致、`(person_id, user_id)` active link 存在、`session.active_account_id == token.user_id`、canonical membership 一致；然后按现有逻辑构建普通账号 `Principal`（`auth_method="person_jwt"`）。所有按"交互式用户"把关的业务面必须通过 `INTERACTIVE_AUTH_METHODS = {"jwt", "person_jwt"}` 判定，使 person token 在业务 API 上与该账号自己的登录 JWT 行为完全一致。

person/session 信息**不得**写入现有账号 `Principal.metadata`。

### 5.11 新端点错误码最小集合

| HTTP | `code` | 使用场景 |
|---:|---|---|
| 400 | `validation_error` / `person_password_weak` / `cannot_bind_super_admin` | 请求字段、密码策略或绑定目标错误 |
| 401 | `authentication_required` / `invalid_person_credentials` / `person_session_invalid` / `invalid_grant` / `invalid_current_password` | 缺少/无效凭据、签名/epoch/session/grant 失效 |
| 403 | `interactive_jwt_required` / `person_session_required` / `super_admin_required` / `admin_required` / `person_disabled` / `account_not_active` | 认证方式或状态不满足；`admin_required` 用于提议 link 的非管理员调用者 |
| 404 | `person_not_found` / `account_not_found` / `account_not_linked` / `link_not_found` | 资源不存在或没有有效关联 |
| 409 | `account_already_linked` / `session_epoch_conflict` / `link_state_conflict` / `active_grant_exists` / `person_number_conflict` | 并发、重复或工号已被其他 person 绑定（登录未传 `account_id` 已改为自动选择，`account_selection_required` 不再返回） |
| 429 | `too_many_attempts` | person 登录/重新认证/enroll 限流或锁定 |
| 503 | `person_auth_unavailable` | 迁移未完成或 person store 未就绪 |

## 6. JWT/session 兼容策略

### 6.1 独立签名密钥与确定性分派

v2 person access JWT **必须使用独立签名密钥**，不得复用 legacy `TOKEN_SECRET`。

- 新增配置 `LIGHTRAG_PERSON_TOKEN_SECRET`：启动时必须非空、非默认值，且与 `TOKEN_SECRET` 不同；相等时启动失败。
- v2 JWT JOSE header：`alg=HS256`、`kid=person-v1`。
- v2 JWT claims（top-level）：`iss=lightrag-person-auth`、`aud=lightrag-api`、`typ=person_access`、`jti`、`sid`（session id）、`person_id`、`user_id`、`person_epoch`、`session_epoch`、`exp`、`iat`。
- **分派规则**：解析时先读 JOSE header `kid`，确定性分派，校验失败后不得跨路径 fallback：
  - 缺失 `kid` header（legacy JWT 本不携带 kid）→ 走 legacy validator（legacy key，无 person claims）。
  - `kid=person-v1` → 走 v2 validator（person key）。
  - 存在 `kid` 但不是 `person-v1` → 直接拒绝。
  - 任何路径签名/校验失败 → 拒绝，不得 fallback 到另一路径。
- 功能开关 `LIGHTRAG_PERSON_AUTH_ENABLED=false` 时，所有 `kid=person-v1` 的 token 一律拒绝；legacy token 不受影响。
- 回滚安全：回滚到旧 binary 后，旧代码没有 person key，天然无法验证 v2 token；回滚前应撤销全部 active person session 或轮换 person signing key。

### 6.2 旧接口和旧 token 不变

1. 旧 `POST /login` 的请求格式、账号密码校验、响应中的既有字段、签名密钥、过期和 `token_version` 语义保持不变。
2. 旧 JWT（无 `kid` 或 legacy kid）按现有逻辑校验签名、过期、账号 active 和账号 `token_version`；不强制查询 person 表。
3. 现有 `/auth/logout`、账号禁用、重置账号密码和管理员 token 失效规则保持原语义。新 person session 仍受账号 `token_version` 影响（account-access 类），但不能反向改变旧接口的语义。

### 6.3 每请求校验顺序

**person_account_access**（业务 API）：

1. 按 `kid` 分派到 v2 validator；验证签名、算法、过期、`iss`/`aud`/`typ`。
2. 按 token `user_id` 读取 `enterprise_users`，检查 active，并执行现有 `token_version` 比较。
3. 按 `person_id` 读取 person 和 active bcrypt credential 状态，检查 person active、`person_epoch` 一致。
4. 按 `session_id` 读取 session，检查 status、`absolute_expires_at`、`person_epoch`、`session_epoch` 一致，且 `active_account_id == token.user_id`。
5. 检查 `(person_id, user_id)` 的 active link 存在。
6. 按现有逻辑加载该账号的 canonical tenant membership、能力位和 KB/业务授权，构造普通账号 `Principal`；设 `request.state.person_session`。

**person_session_control**（accounts/switch/logout/change-password/confirm）：

1-4. 同上 v2/person/session 校验。
5. **跳过**账号 active/token_version/link/membership 检查；switch 时再独立校验目标账号。
6. 设 `request.state.person_session`。

MVP 不使用会延迟撤销生效的长时间内存缓存。

### 6.4 凭据边界

- 普通账号密码只可登录它对应的 `enterprise_users.username`（legacy `/login`），不能作为 person login、accounts、switch 或 enroll 的替代凭据。
- person login 只接受 person 的严格 bcrypt credential；服务端绝不循环尝试该 person 关联的多个账号密码。
- enroll 只接受 super admin 签发的一次性 grant；grant 消费后失效。
- 账号密码变更/账号禁用递增账号 `token_version`，因此该账号的 legacy JWT 和 account-access 类 person token 都失效；**reset password 不是撤销 person link**。要彻底阻止 person 进入某账号，应 disable 账号或 unlink。其它关联账号的 session 不受影响。

## 7. 生命周期与审计

### 7.1 生命周期矩阵

| 操作 | 账号 legacy JWT | person account-access token | person session-control（accounts/switch/logout） | person credential/link |
|---|---|---|---|---|
| 账号 reset password | 旧账号 JWT 失效 | 该账号 token 失效（token_version 变） | 继续有效，可 list/switch/logout | 不变 |
| 账号 disable | 该账号所有访问拒绝 | 该账号 access 拒绝 | 继续有效，可切换其它账号 | link 保留但不能切入 |
| 账号 enable | 需重新签发账号 token | 可重新选择 | person session 可重新选择 | link 不变 |
| 账号 delete | 立即失效 | 立即失效 | active 在该账号的 session `active_account_id` SET NULL 或撤销 | link CASCADE 删除，绑定历史留 audit；其它账号不变 |
| 解绑（unlink） | 原则上仍有效（除非显式递增 token_version） | 该 link 的 access token 失效 | active 在该账号的 session 撤销或置空 | link revoked；其它账号 link 不变 |
| person password change | 不受影响 | 全部失效（epoch 变） | 全部失效（要求重新登录） | credential 轮换 |
| person disable | 不受影响（按账号状态） | 全部失效 | 全部失效 | person disabled，不隐式禁用业务账号 |
| 新 link 激活 | 不受影响 | 旧 session 不得自动获得新账号 | 旧 session 全部撤销，需重新 login | link pending→active，auth_epoch 递增 |

### 7.2 原子事务要求

安全状态变更必须使用 **aggregate atomic store methods**，在一个 `_write()` callback 内完成状态读取/锁定、CAS、多表写入和 audit row 插入：

- `enroll_person_atomic(...)`：消费 grant + 建 person/credential/active link/首个 session + audit。
- `create_person_session_atomic(...)`：login。
- `switch_person_session_atomic(...)`：CAS epoch + 更新 active_account + audit。
- `propose_person_account_link_atomic(...)` / `confirm_person_account_link_atomic(...)` / `revoke_person_account_link_atomic(...)`。
- `rotate_person_credential_atomic(...)` / `disable_person_atomic(...)` / `enable_person_atomic(...)`。
- 账号删除联动：在 `delete_enterprise_user()` 与 `delete_enterprise_user_with_memory()` 两条现有路径中，删除账号前先 revoke 相关 session（`active_account_id` SET NULL），link 由 CASCADE 清理。

**禁止**多个公开 CRUD 拼接成多事务"伪原子"；**禁止**事务内嵌套调用另一公开 `_write()`（非重入锁会死锁）；**禁止**事务内调用公开 `AuditService.append()`（会单独开写事务）。需要内部 `_insert_audit_event(conn, ...)`。登录失败等非授权状态事件可例外独立记录。安全状态变更与审计必须同事务：审计失败则状态变更回滚。

### 7.3 审计事件与可见性

复用现有 `enterprise_audit_events` 结构。事件名：

| 事件 | 触发点 | 可见性 |
|---|---|---|
| `person_enrolled` | enroll 成功 | 平台级 |
| `person_login_succeeded` / `person_login_failed` / `person_login_locked` | person 登录 | 平台级（失败不伪造 actor） |
| `person_account_link_proposed` / `person_account_link_confirmed` / `person_account_unbound` | admin 提议/person 确认/admin 解绑 | 平台级 |
| `person_account_switched` | session 切换（记录 source/target） | 平台级 |
| `person_session_logout` / `person_sessions_logout_all` | 登出 | 平台级 |
| `person_disabled` / `person_enabled` / `person_credential_rotated` | 安全状态变化 | 平台级 |
| `person_enrollment_grant_created` / `person_enrollment_grant_revoked` | grant 签发/撤销 | 平台级 |
| `person_session_revoked_by_account_change` | 账号禁用/解绑/删除导致 session 失效 | 平台级 |

可见性规则：person 身份事件**必须** `actor_tenant_id=None`，不进入 tenant 审计查询；source/target tenant snapshot 与 person/account ID 放仅 super admin 可见的 metadata。tenant audit 接口不得返回 person 事件，也不得对 person 事件的 target user 做 username enrichment。已认证动作的 `actor_user_id` 使用当时选中的账号 ID。不记录明文密码、完整 JWT、grant token 明文、bcrypt 输入或可重放秘密。审计查询沿用现有 super admin 边界。

### 8.2 回滚步骤

1. 将 `LIGHTRAG_PERSON_AUTH_ENABLED` 设为 `false` 并重启；person 路由拒绝请求，`kid=person-v1` token 一律拒绝，legacy `/login` 和无 person claims 的旧 JWT 继续工作。
2. 回滚前应撤销全部 active person session 或轮换 `LIGHTRAG_PERSON_TOKEN_SECRET`，避免旧 binary 误接受（旧 binary 无 person key，天然无法验证 v2）。
3. 不执行 `DROP TABLE` 或破坏性 down migration；新增表保留。若只回滚应用版本，旧代码应能忽略这些额外表。
4. 若发现 link/session 数据风险，先由 super admin 解绑 link、撤销 session 或停用 person，再恢复版本；不得删除 `enterprise_users` 以"回滚关联"。
5. 若 schema 事务失败，依赖数据库事务回滚并从备份恢复。
6. 回滚完成后执行旧认证和账号隔离回归；person 功能重新启用前必须重跑迁移幂等、失效和审计测试。

## 9. 明确禁止的方案与验收标准

### 9.1 明确禁止

1. 禁止 v2 person token 复用 legacy `TOKEN_SECRET`；禁止 v2 校验失败 fallback legacy；禁止未知 kid 静默走 legacy。
2. 禁止按 email、姓名、手机号、username、域名或任何模糊相似度自动关联账号；禁止接入外网 IdP/OIDC/SAML/SSO/LDAP。
3. 禁止让普通账号密码成为跨账号万能钥匙，禁止遍历多个 `enterprise_users` 验证同一密码；禁止"账号 JWT + 账号密码"作为首次 enrollment 凭据。
4. 禁止任何 admin 直接产生 active link；绑定必须 pending→active 且需 person 本人密码确认。tenant admin 的提议权限严格限定为本租户普通成员账号。
5. 禁止把 `person_id` 填入 `Principal.user_id`，禁止把多个账号的 tenant、能力、KB ACL、chat/job 数据合并成一个"自然人 principal"；禁止把 person/session 信息塞进 `Principal.metadata`。
6. 禁止 impersonation、管理员代入、伪造 `X-User-Id`/query 参数切换账号。
7. 禁止存储明文 person password、明文 grant token、raw JWT 或可逆 token；禁止在错误、审计和日志中输出这些值。
8. 禁止为 person 机制复制一套平行 RBAC、绕过现有 tenant membership/KB ACL，或给 person 默认 super admin 权限。
9. 禁止用多个公开 CRUD 拼接成"伪原子"安全状态变更；禁止事务内嵌套 `_write()` 或调用公开 `AuditService.append()`。
10. 禁止迁移阶段静默解决重复 link、孤儿外键或 tenant 冲突；冲突必须失败、回滚并可定位。
11. 禁止把 person 身份事件写入 tenant 审计导致跨 tenant 泄露。
12. 禁止本阶段修改前端或承诺认领邀请通知、密码找回、refresh token、外部通知等未实现功能。

### 9.2 验收标准

- [ ] 新增 person、bcrypt credential、enrollment grant、link、session 五类数据模型在 SQLite 和 PostgreSQL 上可幂等创建；新库、旧库、重复启动和并发启动均通过。
- [ ] v2 person access JWT 使用独立 `LIGHTRAG_PERSON_TOKEN_SECRET`（与 legacy 不同），固定 `kid/iss/aud/typ/jti`，按 kid 确定性分派；v2 不被旧 validator 接受，flag=false 拒绝 v2，回滚后旧 binary 无法验证 v2。
- [ ] person credential 永远以严格 bcrypt 保存/校验；首次 enrollment 只接受 super admin 签发的一次性 grant；账号 `password_hash` 仍只服务 legacy `/login`。
- [ ] admin 绑定只能创建 pending link；person 本人用自然人密码确认后才 active；激活新 link 递增 auth_epoch 并撤销旧 session。没有 email/姓名自动绑定。
- [ ] person login、accounts、switch、logout、logout-all、change-password、grant 签发/撤销、link propose/confirm/unbind、person disable/enable 的请求、响应、权限、错误码与第 5 节一致，并有正向/负向测试。
- [ ] session-control 与 account-access 两类 dependency 行为正确；当前账号 disabled/reset/deleted 后仍能切换或退出。
- [ ] 切换后 `Principal.user_id` 等于目标 `enterprise_users.id`；任何请求都不会同时携带或合并两个账号的 tenant/KB/chat/job/ACL 权限。
- [ ] 安全状态变更使用 aggregate atomic store methods，状态、CAS、多表变更和审计同事务；失败不留 orphan。
- [ ] 账号删除两条路径都正确处理 link/session（CASCADE/SET NULL），无孤儿记录。
- [ ] 一个账号最多一个 active person link；并发绑定、并发切换和并发登出不会产生双绑、旧 token 复活或越权读写。
- [ ] person 身份事件平台级审计（`actor_tenant_id=None`），tenant 审计不泄露跨 tenant person/account 信息。
- [ ] 关键状态变更均有审计记录，记录 actor/tenant/target/结果但不含密码、raw token、grant 明文或 token hash。
- [ ] 关闭 person 功能开关或回滚应用后，旧认证和旧业务数据继续可用；没有破坏性 down migration，也没有删除现有账号数据。
- [ ] **发布 gate 包含真实 PostgreSQL schema、并发、FK、事务回滚和双栈 token 测试。**

只有以上标准全部通过，才能把 person 多账号关联/切换称为本项目的 MVP；在此之前，它只是待实现的后端执行文档。

## 10. 扩展：个人 KB 跨部门共享（在本 MVP 之上实现）

同一自然人多部门账号建立后，个人 KB 可跨部门使用。采用**共享授权**而非 copy/软链接：KB 实体单份（不重建、不复制，归属 `owner_id` 不变），共享在单个 `_write()` 事务内写入 `enterprise_person_kb_shares` 行并物化目标账号的直接 `enterprise_kb_acl`；撤销同事务删除。数据模型、幂等迁移、审计与生命周期规则沿用本文第 4/7 节同一套约束。

硬性规则（与第 3 节不变量并列生效）：

| 编号 | 规则 |
|---|---|
| S-1 | 共享目标只能是**同一 person 的 active link 账号**；owner 必须已 enroll；仅 owner 本人或 super admin 可管理共享。 |
| S-2 | 仅 `origin=platform` 且有 `owner_id` 的个人 KB 可共享；角色限 `kb_viewer/kb_editor/kb_admin`，不转移 `kb_owner`。 |
| S-3 | **共享进部门 ⇒ 该部门 tenant admin/owner 获得监察保底角色**（`person_share_oversight` 授权源，角色取 `LIGHTRAG_ENTERPRISE_TENANT_ADMIN_OVERSIGHT_ROLE`）；部门普通成员不因共享获得任何访问。 |
| S-4 | 共享是目标侧部门作用域的：person link 解绑（任一侧）、目标账号 canonical tenant 变更、账号删除、**租户（部门）删除**、KB purge 均在既有事务内联动撤销共享并清理 ACL；审计事件 `person_kb_share_created/revoked/revoked_by_account_change` 平台级（`actor_tenant_id=None`）。租户删除同时级联清除指向该租户的 tenant-KB ACL 与 per-user override（可撤销授权不阻塞删除；结构性引用仍阻塞）。 |
| S-5 | 共享期间 `(kb_id, target_account_id)` 的 ACL 行由共享机制持有；oversight 谓词实时 JOIN 校验目标账号当前 canonical tenant（fail closed）。 |

端点（`POST/GET /kbs/{kb_id}/person-shares`、`DELETE /kbs/{kb_id}/person-shares/{target_account_id}`、`GET /auth/person/kb-shares`）与错误码详见 `docs/API接口.md` 10.6.11。
