# 多账号身份关联与切换执行文档（后端 API MVP）

> **文档定位**：本文是后端 API MVP 的执行约束、数据契约和验收清单，不表示本文写入时相关功能已经实现。当前代码、现有 JWT 和现有账号数据仍以仓库实现为准；实施时必须先加测试，再逐阶段打开功能开关。
>
> **核心定义**：`person` 是自然人身份；`enterprise_users` 中的一行是一个业务账号（下文简称“账号”）。自然人凭据是跨账号切换的信任根，账号的 `password_hash` 只保留用于 legacy 账号登录。一个自然人可以关联多个账号，但一个账号在任一时刻最多只能有一个有效的自然人关联。

## 1. 当前项目事实

以下事实来自当前仓库的实现和接口契约；行号会随代码变更移动，引用以文件内容为准。

### 1.1 `lightrag/api/metadata_store.py`

- SQLite metadata store 已有 `enterprise_users` 表及 `EnterpriseUserRecord`，账号至少包含 `id`、唯一 `username`、`password_hash`、`system_role`、`status`、`tenant_id`、能力位、`token_version`、metadata 和时间字段。
- `enterprise_tenant_memberships` 以 `(tenant_id, user_id)` 为主键，并通过修复逻辑和 `user_id` 唯一索引保持一个账号只有一个 canonical tenant membership；现有 `enterprise_users.tenant_id` 与该 membership 需要保持一致。
- 个人查询设置、chat project/session/message、chat memory 等记录都带有 `user_id`；KB ACL 也以账号 `user_id` 作为主体键。不能把自然人 ID直接替换成这些记录中的 `user_id`。
- SQLite schema 初始化使用 `CREATE TABLE/INDEX IF NOT EXISTS`，并包含既有数据修复逻辑。新增 person 表应沿用同一初始化/事务路径，不改写既有账号行。
- 现有审计记录 `enterprise_audit_events` 已支持 `event_type`、`actor_user_id`、`actor_tenant_id`、`target_type`、`target_id`、metadata 和创建时间，MVP 优先复用该审计面。

### 1.2 `lightrag/api/enterprise_auth.py`

- `EnterpriseUserRecord` 是当前企业账号的认证和授权数据来源；现有 `authenticate()` 按用户名读取 active 账号并校验账号密码。
- `Principal` 的核心身份字段是 `user_id`，同时携带 `username`、`system_role`、`tenant_id`、`tenant_roles`、能力位、`token_version` 和 `auth_method`。`Principal.user_id` 当前表示账号 ID，不是自然人 ID。
- 现有 token 解析会重新读取账号，校验账号仍为 active，并比较 token 中的 `token_version`；版本不一致时令 token 失效。现有全设备登出、禁用账号、重置账号密码等操作会递增该版本。
- 现有密码辅助逻辑兼容历史账号密码格式。person credential 不得复用其明文回退行为，必须严格保存和校验 bcrypt 值。
- 现有角色包括 `super_admin`、`user` 以及 tenant/KB 角色。person 机制只负责建立信任和选择账号，不自行产生新的 RBAC 角色。

### 1.3 `lightrag/api/routers/enterprise_routes.py`

- 企业路由通过 combined auth 获取当前 principal，并区分普通 principal、interactive JWT 和 service/API key；`/auth/me`、`/auth/logout` 等 self-service 路径要求 interactive JWT。
- 当前已有企业注册、账号管理、tenant membership、KB ACL、审计等路由；管理员路由有 super admin 边界，tenant 管理员不能借此跨 tenant 管理账号。
- 当前文件中没有可视为已实现的 `/auth/person/*` 关联/切换路由。本文所列新路由在代码实现和验收前不得对外宣称可用。

### 1.4 `lightrag/api/postgres_metadata_store.py`

- PostgreSQL metadata store 在初始化时使用事务级 advisory lock，再以原子事务执行 schema 初始化和修复，生产企业模式的 metadata backend 是 PostgreSQL。
- PostgreSQL 现有企业表使用显式列配合 `data_json JSONB`，`enterprise_users`、tenant membership、KB ACL、chat/job 记录均通过账号 ID 关联。
- 现有 membership 的单 tenant 约束和索引在 schema repair 阶段建立；person 新表必须在同一初始化锁和事务中创建，不能只在单进程启动时补表。

### 1.5 `docs/API接口.md`

- 当前 `POST /login` 在企业模式下使用企业用户表，返回包含 `user_id`、`system_role`、`token_version` 等 metadata 的 JWT；该接口是现有账号登录契约。
- 当前 `/auth/logout` 是账号维度的全设备登出，会递增账号 `token_version`。它与本文新增的 person session 登出不是同一个语义，旧接口必须保持不变。
- 现有文档明确企业模式为内网部署，SSO/OIDC/SAML 不在当前认证范围；生产控制面建议使用 PostgreSQL。
- `/admin/*` 的默认管理边界是 super admin，tenant membership 和 KB ACL 仍按账号/tenant 的既有规则执行。

### 1.6 由事实得到的实施边界

本阶段只在现有企业认证之上增加一个“自然人凭据 → 已显式授权账号 → 普通账号 JWT”的薄层。不得借此重构 `enterprise_users`、改变 `Principal.user_id`、合并账号数据，或把尚未实现的 person API 写成当前 API 契约。

## 2. 范围与非目标

### 2.1 本阶段范围

- 纯后端：新增 person/credential/link/session 持久化、SQLite/PostgreSQL 幂等迁移、FastAPI 路由、JWT 校验、审计和自动化测试。
- 部署假设为受控内网。密码、JWT 和 session 查询不依赖外网服务；需要的 bcrypt 在现有 Python 运行时内完成。
- 通过 person credential 登录后，用户只能在有效 link 集合中选择一个账号，并获得该账号语义的普通 JWT。
- 新部门账号由 `super_admin` 使用显式绑定端点绑定；账号自身的创建、tenant membership、KB ACL 和生命周期仍走现有管理面。
- 未来可以在此模型上扩展一次性认领邀请，但邀请不是本 MVP 的实现内容。

### 2.2 明确非目标

- **不接外网 IdP/SSO**：不做 OIDC、SAML、LDAP、OAuth 社交登录、自动目录同步或任何外部身份映射。
- **不做前端**：不修改 Web UI、登录页、路由跳转、状态管理或视觉交互；客户端只按本文的后端契约调用 API。
- **不做 impersonation**：不增加“以某账号身份执行”的管理员代入能力，不允许通过 header、query 参数或隐藏字段伪造 `user_id`。
- 不按 email、姓名、手机号、用户名相似度或模糊匹配自动关联；本阶段没有“发现后自动绑定”。
- 不迁移、合并、复制或重写不同账号的 KB、chat、job、memory、ACL、审计数据。
- 不把普通账号密码改造成 person 密码，也不实现“尝试该自然人所有账号密码”的登录策略。
- 不承诺刷新 token、跨设备共享 token、账号批量自动认领、外部通知或密码找回；如后续需要，另立设计和验收。

## 3. 不变量

下列规则是实现和回归测试必须同时满足的硬约束：

| 编号 | 不变量 | 执行要求 |
|---|---|---|
| I-1 | `enterprise_users` 仍是账号真源 | `account_id` 永远等于现有 `enterprise_users.id`；person 表不复制账号权限字段，也不取代账号密码/状态。 |
| I-2 | 单 tenant membership | 每个账号继续最多一个 canonical tenant；`enterprise_users.tenant_id`、`enterprise_tenant_memberships` 和现有 CAS/repair 规则不因 person link 改变。 |
| I-3 | `Principal.user_id` 是账号 ID | 新 token 解析后仍生成普通 `Principal`，`user_id=当前选中的 enterprise_users.id`；`person_id` 只能作为附加认证 metadata。 |
| I-4 | 业务数据按账号隔离 | KB、chat project/session/message、job、memory、直接 user ACL、个人设置和审计中的账号主体仍按 `user_id`/账号语义过滤；切换不产生数据并集。 |
| I-5 | link 不是授权替代物 | link 只证明该 person 可以选择该账号；账号原有 status、tenant membership、能力位、KB ACL 和 RBAC 仍必须独立校验。 |
| I-6 | person credential 是跨账号信任根 | 只有有效 person credential/session 加上有效 link 才能切换；普通账号 `password_hash` 只支持该账号的 legacy `/login`，不能跨账号使用。 |
| I-7 | 旧认证可继续工作 | 没有 person claims 的旧 `/login` JWT 仍按原有签名、过期时间、`user_id` 和 `token_version` 规则工作；旧客户端不需要感知 person。 |
| I-8 | 失效及时生效 | 每次使用新 person token 都校验账号、person、session、epoch 和 link；不能用不一致的长缓存绕过 logout、解绑、禁用或密码重置。 |
| I-9 | 绑定必须显式 | 首次 enroll 只可把当前已认证账号建立为初始 link；其它/新部门账号只能由 `super_admin` 用 account ID 显式绑定，不能由 email/姓名/用户名自动推断。 |
| I-10 | 一个账号不共享自然人信任 | 同一账号最多一个 active person link；并发绑定必须由数据库唯一约束裁决，不能出现两个 person 都能切换到同一账号的竞态状态。 |

## 4. 数据模型与幂等迁移

以下是建议的逻辑模型和表名。表名使用 `enterprise_` 前缀以避免与其它 metadata 表冲突；这是待实现的 schema，不代表当前数据库已经存在。

### 4.1 `enterprise_persons`（person）

| 字段 | 要求 |
|---|---|
| `id` | `TEXT PRIMARY KEY`，服务端生成不透明 ID，例如 `per_<hex>`；不得把 email/姓名作为主键。 |
| `status` | `active` / `disabled`；禁止用删除来代替停用。 |
| `auth_epoch` | 整数，初始为 `1`；person 密码变更、停用、logout-all 等全局撤销操作递增。 |
| `metadata_json`（SQLite）/`data_json`（PostgreSQL） | 仅存非安全显示 metadata；不存明文密码、raw JWT 或可恢复的 token。 |
| `created_at`、`updated_at` | UTC 时间，非空。 |

MVP 不增加 email、手机号或可用于自动匹配的外部身份字段。若需要显示名，只能是显式设置的展示属性，不能作为绑定条件。

### 4.2 `enterprise_person_credentials`（person credential）

| 字段 | 要求 |
|---|---|
| `id` | credential ID，主键。 |
| `person_id` | 非空外键，指向 `enterprise_persons.id`。 |
| `credential_type` | MVP 固定为 `password`。 |
| `algorithm` | MVP 固定为 `bcrypt`。 |
| `password_hash` | 只保存 bcrypt 结果，建议沿用现有 `{bcrypt}$2b$...` 表示；严格禁止明文回退。 |
| `status` | `active` / `revoked`。 |
| `failed_count`、`locked_until`、`last_used_at` | 用于跨 worker 的登录失败控制和运维观察；失败计数更新必须原子化。 |
| `created_at`、`updated_at` | UTC 时间，非空。 |

约束：`UNIQUE(person_id, credential_type)`，MVP 每个 person 只有一个 active password credential；密码轮换更新该行并递增 `enterprise_persons.auth_epoch`。bcrypt cost 复用现有运行环境基线，不在请求中降低 cost；person 密码校验不得调用允许明文 legacy fallback 的路径。

### 4.3 `enterprise_person_account_links`（person-account link）

| 字段 | 要求 |
|---|---|
| `id` | link ID，主键。 |
| `person_id` | 非空外键，指向 person。 |
| `account_id` | 非空外键，指向 `enterprise_users.id`；这是唯一允许的绑定键。 |
| `status` | `active` / `revoked`。 |
| `bound_by`、`bound_at` | 初始 enroll 可记录当前账号；管理绑定必须记录 super admin 账号和时间。 |
| `revoked_by`、`revoked_at`、`reason` | 解绑和异常处置的审计信息。 |
| `created_at`、`updated_at` | UTC 时间，非空。 |

约束和索引：

1. `UNIQUE(person_id, account_id)`，已撤销的 pair 重新绑定时更新/恢复原行，不插入重复历史行。
2. 对 `status='active'` 建立 `UNIQUE(account_id)` 的部分唯一索引；一个账号不能被两个 person 同时有效关联。
3. 建立 `(person_id, status)`、`(account_id, status)` 索引；所有读取只取 active link，并再次检查账号状态。
4. 目标为 `system_role=super_admin` 的账号默认禁止绑定，除非另行批准安全设计；MVP 不借 person 机制扩大 super admin 面。

### 4.4 `enterprise_person_login_sessions`（login session）

| 字段 | 要求 |
|---|---|
| `id` | session ID，例如 `psess_<hex>`，主键。 |
| `person_id` | 非空外键，指向 person。 |
| `active_account_id` | 当前选中的 `enterprise_users.id`；切换时原子更新。 |
| `token_hash` | 对 JWT 的 `jti` 或等价随机 session secret 做单向 hash；唯一，绝不保存 raw token。 |
| `status` | `active` / `revoked` / `expired`。 |
| `person_epoch` | 签发时复制 person 的 `auth_epoch`。 |
| `session_epoch` | 每次 switch 或当前 session logout 递增/终止；用于拒绝旧 token。 |
| `created_at`、`expires_at`、`last_seen_at`、`revoked_at` | UTC 时间，非空字段按状态要求填写。 |

MVP 允许同一 person 多设备多 session；不提供 refresh token。每次请求必须同时满足：session active 且未过期、token 的两种 epoch 与数据库一致、person active、`active_account_id` 存在 active link、账号 active。切换成功后签发新 token，旧 token 因 `session_epoch` 不一致立即失效。

### 4.5 SQLite/PostgreSQL 幂等迁移要求

- **不修改既有核心表结构**：不向 `enterprise_users` 填 person ID，不重命名 `user_id`，不把现有数据复制到 person 表作为“自动迁移”。
- **SQLite**：在现有 metadata schema 初始化事务中加入四张新表，使用 `CREATE TABLE IF NOT EXISTS`、`CREATE INDEX IF NOT EXISTS` 和 `CREATE UNIQUE INDEX IF NOT EXISTS`；开启外键检查。部分唯一索引示意：

  ```sql
  CREATE UNIQUE INDEX IF NOT EXISTS uq_person_account_active
  ON enterprise_person_account_links(account_id)
  WHERE status = 'active';
  ```

- **PostgreSQL**：在 `PostgresMetadataStore.initialize()` 已有 advisory lock 的事务中创建四张表和索引，使用 `IF NOT EXISTS`、明确的 `CHECK/UNIQUE/FOREIGN KEY`，并用 `ON CONFLICT` 处理 schema version/幂等写入。部分唯一索引使用同等的 `WHERE status = 'active'` 条件。
- 新表创建、索引创建、schema version 记录和必要的修复必须可重复执行；首次启动、重复启动和多个 worker 并发启动都不能产生重复表、重复索引或半迁移状态。
- 迁移前先备份数据库并检查新表中的 active link 冲突；若发现冲突或外键孤儿，迁移应失败并回滚，不能静默选择 person 或账号。
- 初始数据只通过显式 enroll/管理绑定产生。不得以 email、姓名、手机号、username、大小写模糊匹配或相似度回填 link。
- 账号删除、停用和 tenant 变更的现有事务必须在提交前处理关联 link/session；禁止留下可继续签发 token 的孤儿记录。是否采用数据库级联不能替代撤销、审计和测试。

## 5. MVP API 草案

> 下列路径是待实现的 API 草案。除现有 `/login`、`/auth/logout` 等兼容接口外，未实现前不得在部署说明中宣称可调用。所有新端点默认受建议的 `LIGHTRAG_PERSON_AUTH_ENABLED=false` 开关保护；该配置名本身也是待实现配置。

### 5.1 通用约定

- JSON 请求使用 `Content-Type: application/json`。需要 person session 的端点使用 `Authorization: Bearer <new-person-token>`；service/scoped API key 不可代替 person session。
- 成功返回的 `account` 对象只包含 `account_id`、`username`、`status`、`system_role`、`tenant_id`、`tenant_roles` 等非秘密字段，不返回 `password_hash`、完整 metadata、token hash 或原始凭据。
- 错误外层沿用项目 HTTP 错误处理，逻辑错误码必须稳定。建议形态：

  ```json
  {
    "detail": {
      "code": "account_not_linked",
      "message": "Account is not linked to this person",
      "request_id": "req_..."
    }
  }
  ```

- 密码校验失败、person 不存在、credential 不存在和账号选择不合法不得泄露不必要的账号发现信息；登录失败使用统一错误文本并限流。
- token 响应统一包含 `access_token`、`token_type: "bearer"`、`expires_in`、`person`、`active_account`、`session`。新 token 的业务身份仍是 `active_account`。

### 5.2 `POST /auth/person/enroll`

**用途**：当前已登录账号创建一个 person，并把当前账号作为第一个有效 link；创建 person、bcrypt credential、link 和首个 session 必须在一个事务中完成。

**请求**（需要现有账号 JWT，并要求重新输入当前账号密码）：

```json
{
  "current_account_password": "当前账号密码",
  "person_password": "自然人密码"
}
```

**权限**：`auth_method=jwt`、当前账号 active、当前 token 通过现有 `token_version` 检查；必须验证 `current_account_password`。API key、service key、无 token 请求返回 `403`/`401`。该重新认证只证明当前账号所有权，不授权其它账号。

**成功**：`201 Created`，返回新 person ID、当前账号摘要和首个 person session token。person password 只写入严格 bcrypt hash。

```json
{
  "access_token": "<new-person-jwt>",
  "token_type": "bearer",
  "expires_in": 3600,
  "person": {"person_id": "per_...", "status": "active"},
  "active_account": {"account_id": "usr_dept_a", "username": "alice_finance", "status": "active", "tenant_id": "tenant_finance", "system_role": "user"},
  "session": {"session_id": "psess_...", "expires_at": "2026-07-29T12:00:00Z"}
}
```

**主要错误**：

- `400 validation_error` / `person_password_weak`：字段缺失、超长、空白或不满足密码策略。
- `401 authentication_required` / `account_reauth_failed`：没有有效账号 JWT 或当前账号密码不匹配。
- `403 interactive_jwt_required` / `account_not_active`：API key、service key、账号 disabled/pending。
- `409 account_already_linked`：当前账号已经有 active link；不得再创建第二个 person。
- `429 too_many_attempts`：重新认证触发登录保护。

### 5.3 `POST /auth/person/login`

**用途**：使用 person credential 登录，并选择一个已经显式关联且 active 的账号。

**请求**：

```json
{
  "person_id": "per_...",
  "person_password": "自然人密码",
  "account_id": "usr_dept_a"
}
```

`account_id` 在 person 只有一个 active link 时可以省略；有多个 active link 时必须显式提供。服务端只按精确 `person_id + account_id` 查找，不接受 email/姓名/用户名推断。

**权限**：公开登录入口（受 person 功能开关、bcrypt 校验、失败计数和限流保护），不接受 API key 作为认证材料。只有 credential 校验成功且 link、账号状态均有效时才创建 session。

**成功**：`200 OK`，返回与 enroll 相同形状的 person token 响应。token 的 `user_id` 是请求选择的账号 ID。

**主要错误**：

- `401 invalid_person_credentials`：person、密码或 credential 不匹配，统一返回，不区分具体原因。
- `403 person_disabled` / `account_not_active`：person 或目标账号不可用。
- `409 account_selection_required`：密码正确但有多个 active link 且未提供 `account_id`；响应可返回该已认证 person 可见的账号摘要。
- `404 account_not_linked`：指定账号不是该 person 的 active link；不得尝试其它账号密码。
- `429 too_many_attempts`：失败次数达到保护阈值，带 `Retry-After`。

### 5.4 `GET /auth/person/accounts`

**用途**：列出当前 person 可选择的账号，供切换前确认。

**请求/权限**：无请求体；必须是有效的新 person session。旧 `/login` JWT、API key、service key 返回 `403 person_session_required`。该端点只返回该 person 的 active link 对应账号；当前账号若已被禁用，可在此显示为 disabled 以便切换到其它 active 账号，但不能借此访问业务数据。

**成功**：`200 OK`。

```json
{
  "person": {"person_id": "per_...", "status": "active"},
  "active_account_id": "usr_dept_a",
  "accounts": [
    {"account_id": "usr_dept_a", "username": "alice_finance", "status": "active", "tenant_id": "tenant_finance", "system_role": "user"},
    {"account_id": "usr_dept_b", "username": "alice_legal", "status": "active", "tenant_id": "tenant_legal", "system_role": "user"}
  ]
}
```

**主要错误**：`401 person_session_invalid`、`403 person_disabled`、`503 person_auth_unavailable`。响应不得包含密码、token hash 或未关联账号。

### 5.5 `POST /auth/person/switch`

**用途**：在当前 person 的 active link 集合内切换账号，并签发新的账号作用域 JWT。

**请求**：

```json
{"account_id": "usr_dept_b"}
```

**权限**：有效新 person session；目标账号必须是该 person 的 active link、账号 active、tenant/RBAC 数据本身有效。无需输入目标账号密码，也不允许把目标账号密码作为切换凭据。

**事务语义**：锁定 session 和 link，确认 person/session epoch 未变化，更新 `active_account_id`，递增 `session_epoch`，再签发新 token。旧 token 必须立即因 epoch 不一致失败；切换不迁移或合并任何业务数据。

**成功**：`200 OK`，返回新的 token 响应，`active_account.account_id` 和 token `user_id` 均为目标账号。

**主要错误**：

- `401 person_session_invalid`：签名、过期、session 状态或 epoch 不合法。
- `403 person_disabled` / `account_not_active`：person 或目标账号不可用。
- `404 account_not_linked`：目标账号没有该 person 的 active link。
- `409 session_epoch_conflict`：并发切换/登出导致 CAS 失败，客户端重新登录或重新读取 accounts。

### 5.6 `POST /auth/person/logout`

**用途**：仅撤销当前 person login session。

**请求/权限**：无请求体；必须是当前有效的新 person session，不接受普通账号密码或 API key。

**成功**：`200 OK`。

```json
{"status": "logged_out", "session_id": "psess_..."}
```

实现上把 session 标记为 `revoked`（或递增其 epoch），同一 token 的后续请求返回 `401 person_session_invalid`。不改变其它 session，也不改变现有 `/auth/logout` 的账号维度语义。

### 5.7 `POST /auth/person/logout-all`

**用途**：撤销该 person 的全部 session。

**请求/权限**：无请求体；必须是有效新 person session。person disabled、凭据轮换和安全处置也应复用同一全局 epoch 机制。

**成功**：`200 OK`。

```json
{"status": "logged_out_all", "revoked_sessions": 2}
```

事务中递增 `enterprise_persons.auth_epoch` 并撤销所有 active session；当前和其它设备的 person token 后续均返回 `401`。账号本身的 legacy `/login` token 不因 person logout-all 被误改写，除非同时执行现有账号 logout/禁用操作。

### 5.8 super admin 显式绑定/解绑账号

#### `PUT /admin/persons/{person_id}/accounts/{account_id}`

**请求**：

```json
{"reason": "新部门账号显式绑定"}
```

`person_id` 和 `account_id` 必须是服务端生成/存量记录的精确 ID；不接受 email、姓名、username 搜索代替路径 ID。

**权限**：仅 active `super_admin` 的 interactive JWT。tenant_admin、tenant_owner、普通账号、service/scoped API key 和“知道账号密码”的调用方均无权绑定。目标必须是存在的非 super-admin 账号；账号可暂时 pending/disabled，但在 active 前不能登录或切换。

**成功**：`200 OK`（已有同一 active link 时幂等返回）或 `201 Created`，返回 link/account 摘要；不替 person 签发 token。数据库唯一约束处理并发绑定。

**主要错误**：`401 authentication_required`、`403 super_admin_required`、`404 person_not_found/account_not_found`、`409 account_already_linked`、`400 cannot_bind_super_admin`。

#### `DELETE /admin/persons/{person_id}/accounts/{account_id}`

**请求/权限**：无请求体；权限与 PUT 相同。

**成功**：`200 OK`，例如：

```json
{"status": "unlinked", "person_id": "per_...", "account_id": "usr_dept_b", "revoked_sessions": 1}
```

解绑只撤销 link，不删除 `enterprise_users`、tenant、KB、chat、job、ACL 或审计数据；所有以该账号为 active account 的 person sessions 必须在同一事务中撤销或使其失效。其它账号的 session 不受影响。无 active link 返回 `404 link_not_found`；并发状态变化返回 `409 link_state_conflict`。

### 5.9 新端点错误码最小集合

| HTTP | `code` | 使用场景 |
|---:|---|---|
| 400 | `validation_error` / `person_password_weak` | 请求字段或密码策略错误 |
| 401 | `authentication_required` / `invalid_person_credentials` / `person_session_invalid` | 缺少/无效凭据、签名/epoch/session 失效 |
| 403 | `interactive_jwt_required` / `person_session_required` / `super_admin_required` / `person_disabled` / `account_not_active` | 认证方式或状态不满足 |
| 404 | `person_not_found` / `account_not_found` / `account_not_linked` / `link_not_found` | 资源不存在或没有有效关联 |
| 409 | `account_already_linked` / `account_selection_required` / `session_epoch_conflict` / `link_state_conflict` | 并发、重复或需要明确选择 |
| 429 | `too_many_attempts` | person 登录/重新认证限流或锁定 |
| 503 | `person_auth_unavailable` | 迁移未完成或 person store 未就绪 |

## 6. JWT/session 兼容策略

### 6.1 旧接口和旧 token 不变

1. 旧 `POST /login` 的请求格式、账号密码校验、响应中的既有字段、签名密钥、过期和 `token_version` 语义保持不变。
2. 旧 JWT 没有 person/session claims 时，按现有逻辑校验签名、过期、账号 active 和账号 `token_version`；不强制查询 person 表，以免旧客户端和旧数据被新机制阻断。
3. 现有 `/auth/logout`、账号禁用、重置账号密码和管理员 token 失效规则保持原语义。新 person session 仍受账号 `token_version` 影响，但不能反向改变旧接口的语义。

### 6.2 新 token 只增加 person/session/epoch metadata

新 token 沿用现有 JWT 结构和账号 claims，只增加以下 metadata（键名以最终实现和现有 token serializer 对齐）：

```json
{
  "auth_mode": "enterprise",
  "user_id": "usr_dept_b",
  "tenant_id": "tenant_legal",
  "system_role": "user",
  "token_version": 7,
  "person_id": "per_...",
  "session_id": "psess_...",
  "person_epoch": 2,
  "session_epoch": 4
}
```

- 不把 `person_id` 放入 `Principal.user_id`；业务层收到的仍是 `user_id=usr_dept_b`。
- 不把多个账号的 tenant、能力位或 ACL 合并进一个 token。每个 token 只有一个当前账号上下文。
- token 只保存必要的 ID/epoch，不保存 password、token raw value、账号密码 hash 或账号列表。

### 6.3 每请求校验顺序

对含 person metadata 的 JWT，每个受保护请求至少执行：

1. 验证 JWT 签名、算法、过期时间和基本格式。
2. 按 token `user_id` 读取 `enterprise_users`，检查 active，并执行现有 `token_version` 比较。
3. 按 `person_id` 读取 person 和 active bcrypt credential 状态，检查 person active、`person_epoch` 一致。
4. 按 `session_id` 读取 session，检查 status、expires_at、`person_epoch`、`session_epoch` 一致。
5. 检查 `(person_id, user_id)` 的 active link 存在，并确认 session 的 `active_account_id` 与 token `user_id` 一致。
6. 按现有逻辑加载该账号的 canonical tenant membership、能力位和 KB/业务授权，构造普通 `Principal`。

MVP 不使用会延迟撤销生效的长时间内存缓存；若未来加缓存，必须有不弱于上述每请求失效语义的版本/广播机制，并另行验收。

### 6.4 凭据边界

- 普通账号密码只可登录它对应的 `enterprise_users.username`（legacy `/login`），不能作为 person login、accounts 或 switch 的替代凭据。
- person login 只接受 person 的严格 bcrypt credential；服务端绝不循环尝试该 person 关联的多个账号密码。
- enroll 的 `current_account_password` 只是当前账号的二次确认，成功后也只建立当前账号的初始 link；它不是跨账号万能钥匙。
- 账号密码变更/账号禁用递增账号 `token_version`，因此该账号的旧 JWT 和 person token 都失效；不会把其它关联账号一起注销。

## 7. 生命周期与审计

### 7.1 生命周期状态和动作

| 对象 | 生命周期规则 |
|---|---|
| person | `active → disabled` 时递增 `auth_epoch` 并撤销全部 session；MVP 不硬删除 person，以保留审计关联。 |
| credential | 只保留一个 active bcrypt password credential；轮换时原子更新 hash、递增 person epoch、撤销全部 session。 |
| link | `active → revoked` 是软撤销；解绑不删除账号及其业务数据。重新绑定同一 pair 复用/恢复唯一 pair 行并重新审计。 |
| session | `active → revoked/expired`；单 session logout 只影响当前 session，logout-all/credential/person 状态变更影响全部 session。 |
| enterprise account | 仍由现有账号管理流程创建、enable、disable、reset-password、delete；任何状态变更都必须让 person token 的账号检查立即失效或拒绝。 |

执行规则：

- 首次 enroll 只能由当前账号的有效 JWT + 当前账号密码显式发起；它不扫描其它账号。
- 新部门账号先按现有流程创建，再由 super admin 以明确 `account_id` 绑定；不存在“账号创建后自动归属某 person”。
- 解绑、账号删除或账号从 tenant 移除时，先处理相关 link/session，再提交现有账号变更；失败要整体回滚。
- person session 只能访问当前选中账号的数据；不能因为同一个 person 还关联其它账号而读取其它账号的 KB/chat/job/ACL。
- 认领邀请、审批流、密码找回、设备管理等后续能力不在本阶段，不在验收中视为已提供。

### 7.2 审计事件

复用现有 `enterprise_audit_events` 记录结构。建议事件名如下，最终命名须在代码常量和测试中固定：

| 事件 | 触发点 |
|---|---|
| `person_enrolled` | enroll 成功并建立首个 link/session。 |
| `person_login_succeeded` / `person_login_failed` / `person_login_locked` | person 登录成功、失败、触发锁定。 |
| `person_account_bound` / `person_account_unbound` | super admin 显式绑定/解绑。 |
| `person_account_switched` | session 切换成功，记录来源/目标账号。 |
| `person_session_logout` / `person_sessions_logout_all` | 单 session 或全 person session 登出。 |
| `person_disabled` / `person_credential_rotated` | person 安全状态变化。 |
| `person_session_revoked_by_account_change` | 账号禁用、重置密码、解绑等导致 session 失效。 |

审计字段要求：

- 已认证动作的 `actor_user_id` 使用当时选中的账号 ID，`actor_tenant_id` 使用事件时 tenant 快照；person ID、session ID、目标账号和原因放入 metadata/target 字段。
- 未认证登录失败不伪造 actor；可记录规范化失败类型、request ID 和时间，但不记录明文密码、完整 JWT、token hash、bcrypt 输入或可重放秘密。
- 绑定/解绑/切换/登出等状态变更与状态写入必须在同一事务内完成，或在现有审计 service 不能参与事务时建立明确的失败告警和补偿记录，不能返回成功却静默丢审计。
- 审计查询沿用现有 super admin/tenant 过滤边界；不能因为 person 关联而让 tenant 管理员看到其它 tenant 的账号或审计。

## 8. 分阶段实施、回滚与验证

### 8.1 分阶段实施

| 阶段 | 交付物 | 开关/出口条件 |
|---|---|---|
| 0. 基线 | 备份 SQLite/PostgreSQL，固定旧 `/login`、旧 JWT、RBAC 和数据隔离基线测试；确认 `LIGHTRAG_PERSON_AUTH_ENABLED` 默认关闭。 | 基线全绿，备份可恢复。 |
| 1. 数据层 | 四张 person 表、严格 bcrypt、SQLite/PG 幂等迁移、唯一约束、store contract 和 migration tests；不挂新路由。 | 新鲜库、已有库、重复初始化、并发初始化均通过。 |
| 2. 认证层 | enroll/login/session token、每请求 epoch/link 校验、accounts/switch/logout/logout-all；仍默认关闭新入口。 | 旧认证回归通过；新 token 可被撤销且不改变 Principal.user_id。 |
| 3. 管理与审计 | super admin 显式绑定/解绑、并发 CAS、账号生命周期联动、审计事件和安全负向测试。 | 只能显式绑定，所有敏感动作可追溯。 |
| 4. 内网试运行 | 仅在测试/内网环境打开开关，运行 smoke、并发和回滚演练；确认无跨账号数据可见性。 | 验收标准全部通过后才可扩大启用范围。 |

### 8.2 回滚步骤

1. 将建议配置 `LIGHTRAG_PERSON_AUTH_ENABLED` 设为 `false` 并重启/热加载；新 person 路由拒绝请求，新 person token 不再通过 person 校验，旧 `/login` 和无 person claims 的旧 JWT 继续工作。
2. 不执行 `DROP TABLE` 或破坏性 down migration；新增表保留，便于取证和重新启用。若只回滚应用版本，旧代码应能忽略这些额外表。
3. 若发现 link/session 数据风险，先由 super admin 解绑相关 link、撤销 person sessions 或停用 person，再恢复应用版本；不得删除 `enterprise_users` 以“回滚关联”。
4. 若 schema 事务失败，依赖数据库事务回滚并从备份恢复；确认既有表行数、schema version、旧 token 和核心业务读写均正常后再继续。
5. 回滚完成后执行旧认证和账号隔离回归；person 功能重新启用前必须重跑迁移幂等、失效和审计测试。

## 9. 明确禁止的方案与验收标准

### 9.1 明确禁止

1. 禁止按 email、姓名、手机号、username、域名或任何模糊相似度自动关联账号；本阶段不做外网身份自动关联。
2. 禁止接入外网 IdP、OIDC、SAML、SSO、LDAP 或后台自动目录同步。
3. 禁止让普通账号密码成为跨账号万能钥匙，禁止遍历多个 `enterprise_users` 验证同一个密码。
4. 禁止把 `person_id` 填入 `Principal.user_id`，禁止把多个账号的 tenant、能力、KB ACL、chat/job 数据合并成一个“自然人 principal”。
5. 禁止 impersonation、管理员代入、伪造 `X-User-Id`/query 参数切换账号，或以“当前账号可见账号列表”绕过 link/状态校验。
6. 禁止存储明文 person password、明文账号密码、raw JWT、refresh secret 或可逆 token；禁止在错误、审计和日志中输出这些值。
7. 禁止为 person 机制复制一套平行 RBAC、绕过现有 tenant membership/KB ACL，或给 person 默认 super admin 权限。
8. 禁止迁移阶段静默解决重复 link、孤儿外键或 tenant 冲突；冲突必须失败、回滚并可定位。
9. 禁止本阶段修改前端或承诺认领邀请、密码找回、刷新 token、外部通知等未实现功能。

### 9.2 验收标准

- [ ] 新增 person、bcrypt credential、link、session 四类数据模型在 SQLite 和 PostgreSQL 上可幂等创建；新库、旧库、重复启动和并发启动均通过。
- [ ] person credential 永远以严格 bcrypt 保存/校验；账号 `password_hash` 仍只服务 legacy `/login`，两者没有跨账号替代关系。
- [ ] enroll 只能以当前账号 JWT + 当前账号密码建立初始 link；新部门账号只能由 super admin 用精确 account ID 显式绑定；没有 email/姓名自动绑定。
- [ ] person login、accounts、switch、logout、logout-all 和 super admin bind/unbind 的请求、响应、权限、错误码与第 5 节一致，并有正向/负向测试。
- [ ] 新 token 只在既有账号 JWT 语义上增加 person/session/epoch metadata；每请求校验签名、账号 `token_version`、person、session、epoch、link 和账号状态。
- [ ] 切换后 `Principal.user_id` 等于目标 `enterprise_users.id`；任何请求都不会同时携带或合并两个账号的 tenant/KB/chat/job/ACL 权限。
- [ ] 单 session logout、person logout-all、解绑、账号禁用/密码重置的失效边界符合第 6、7 节；旧 `/login`/旧 JWT 和现有 `/auth/logout` 回归不变。
- [ ] 一个账号最多一个 active person link；并发绑定、并发切换和并发登出不会产生双绑、旧 token 复活或越权读写。
- [ ] 关键状态变更均有现有审计记录，记录 actor/tenant/target/结果但不含密码、raw token 或 token hash。
- [ ] 关闭 person 功能开关或回滚应用后，旧认证和旧业务数据继续可用；没有破坏性 down migration，也没有删除现有账号数据。

只有以上标准全部通过，才能把 person 多账号关联/切换称为本项目的 MVP；在此之前，它只是待实现的后端执行文档。
