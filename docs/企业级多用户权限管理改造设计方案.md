# LightRAG 企业级多用户管理与权限改造设计方案

> 文档版本：2026-06-07  
> 适用范围：在现有 `/kbs/...` 知识库 API、JWT/API-Key 认证、KB workspace 隔离、SQLite/PostgreSQL control-plane metadata 之上，新增企业级多用户、注册控制、RBAC/ACL、审计与运维治理能力。  
> 目标读者：后端实现者、前端实现者、部署运维、测试/安全审计人员。  
> 关联文档：`docs/API接口文档.md`、`docs/生产级后端改造设计方案.md`、`docs/生产级后端改造待办清单.md`。

## 0. 实施状态（2026-06-07）

本轮已完成**后端企业模式 MVP**，并保持默认关闭以兼容现有单用户/API-Key 部署：

- 已新增 `.env` 企业模式配置：`LIGHTRAG_ENTERPRISE_AUTH_ENABLED`、`LIGHTRAG_SUPER_ADMIN_USERNAME`、`LIGHTRAG_SUPER_ADMIN_PASSWORD`、`LIGHTRAG_SUPER_ADMIN_PASSWORD_HASH`、`LIGHTRAG_USER_REGISTRATION_ENABLED`、`LIGHTRAG_ENTERPRISE_DISABLE_GLOBAL_ROUTES`、`LIGHTRAG_ENTERPRISE_LEGACY_API_KEY_SUPERADMIN`。
- 已实现启动校验：企业模式必须使用非默认 `TOKEN_SECRET`，并必须配置超级管理员用户名和密码/密码 hash。
- 已实现 SQLite/PostgreSQL metadata parity：`enterprise_users`、`enterprise_system_settings`、`enterprise_kb_acl`、`enterprise_audit_events` 及对应 public store methods。
- 已实现 metadata-backed 企业 principal、超级管理员 bootstrap、用户登录校验、token_version 失效、注册开关、用户创建/更新/密码变更、KB ACL 授权/撤销、审计写入。
- 已实现企业模式下 `/auth-status` 不再签发 guest token，`/login` 使用企业用户表认证。
- 已新增企业 API：`/auth/register`、`/auth/me`、`/auth/change-password`、`PATCH|PUT /admin/settings/registration`、`/admin/users`、`/admin/kbs/{kb_id}/acl`、`/admin/audit-events`。
- 已在 `/kbs/...` 路由边界接入 fail-closed RBAC：创建 KB 需要 `can_create_kb` 或 super admin；KB 列表按 ACL 过滤；KB 创建时忽略请求体伪造的 `owner_id`/`tenant_id` 并自动写 `kb_owner` ACL；KB 更新在企业模式下忽略请求体伪造的 `owner_id`/`tenant_id`；配置版本 `created_by` 在企业模式下来自 principal；`DELETE /kbs/{kb_id}` soft/hard delete 为 super-admin-only 并写审计；query/graph/document/config 路径通过集中依赖按 KB role 检查；最终解析后的 `mode="bypass"`（包括 active query config 默认值）需要额外 `can_use_bypass_query`。
- 已实现企业模式 anti-bypass：受保护前缀不能被 `WHITELIST_PATHS` 放行；全局 `LIGHTRAG_API_KEY` 默认不能绕过企业 RBAC；legacy/global `/documents`、`/query`、`/graph`、`/api` 默认禁用或 super-admin-gated（取决于显式 legacy 开关）。

本轮暂未实现：完整前端管理台、per-KB/service API key、配额/限流、复杂租户组织树、SSO/OIDC/SAML、细粒度 artifact 字段级权限。这些仍按本文后续章节作为后续阶段扩展。

## 1. 背景与当前状态

当前 LightRAG API Server 已具备较完整的 KB 生产主链路：KB CRUD、文档上传/解析/构建/查询、任务中心、配置版本、对象存储、PostgreSQL metadata 后端、durable worker 等均已落地。

但用户与权限体系仍停留在“全局认证门”阶段：

- `lightrag/api/auth.py` 从 `AUTH_ACCOUNTS` 读取静态账号，登录后签发 JWT，token 内只有基础 `role` 字段。
- `lightrag/api/utils_api.py::get_combined_auth_dependency()` 只验证白名单路径、Bearer JWT 或全局 `X-API-Key`，不返回当前用户 principal，也不感知 `kb_id`。
- `/kbs/...` 系列 route 目前普遍使用 `dependencies=[Depends(combined_auth)]`，handler 内拿不到当前用户。
- KB catalog 的 `owner_id` / `tenant_id` / `visibility` 只是预留字段，未参与查询过滤或权限判断。
- 当前任意有效全局 API Key 或任意有效非 guest JWT 理论上可以访问任意 KB；`DELETE /kbs/{kb_id}` 和 `mode="bypass"` 也未按角色限制。

因此，本方案将 Phase 6 平台能力补齐为**显式的企业级用户/RBAC/ACL 层**，并要求所有权限在服务端 route 边界强制执行。

## 2. 改造目标

### 2.1 必须满足的用户需求

1. **`.env` 配置超级管理员**
   - 部署时可通过 `.env` 配置超级管理员用户名与初始凭证。
   - 系统首次启动时自动创建或同步该超级管理员。

2. **超级管理员实时控制是否启用用户注册**
   - 注册开关不能只依赖重启时读取 `.env`；需要持久化配置并提供管理 API。
   - 超级管理员可在运行时开启/关闭注册。

3. **超级管理员给不同用户授予不同权限**
   - 用户是否可以创建新的知识库。
   - 用户可以访问/使用哪些已有知识库。
   - 用户在每个知识库内的角色不同：只读、编辑、管理等。

4. **删除知识库仅超级管理员有资格**
   - `DELETE /kbs/{kb_id}` soft delete 和 `DELETE /kbs/{kb_id}?hard=true` hard delete 都必须 super-admin-only。

### 2.2 企业级补充目标

1. 支持用户禁用、锁定、重置密码、强制登出。
2. 支持租户/组织预留，方便后续 SaaS 化。
3. 支持服务账号 / per-KB API Key，替代全局 `LIGHTRAG_API_KEY` 的无限权限。
4. 支持审计日志：登录、注册、用户变更、权限变更、KB 创建/删除、文档操作、查询、配置变更。
5. 支持配额与限流：KB 数量、上传大小、并发任务、查询速率、token 预算。
6. 支持安全默认值：企业模式默认禁用 guest、禁用匿名注册、禁用全局 API Key 绕过 RBAC。
7. 支持平滑迁移：默认单用户部署不受影响；开启企业模式后再执行严格权限。

## 3. 非目标与边界

本方案第一期不实现以下能力，但会预留扩展点：

- 外部 SSO / OIDC / SAML 单点登录。
- 细粒度字段级权限，例如“允许查看文档列表但不允许下载 artifact”。第一期先用 role + permission 组合覆盖主路径。
- 复杂组织层级、跨租户共享、计费结算。
- 前端完整管理后台实现细节；本文只定义后端能力和 UI 需求。

## 4. 设计原则

1. **Fail Closed**：企业模式下无法确认身份或权限时，一律拒绝。
2. **服务端强制权限**：前端只做展示优化，不能承担安全职责。
3. **最小权限**：新注册用户默认无 KB 权限、不可创建 KB。
4. **超级管理员最小暴露**：超级管理员用于平台级治理，不建议用于日常数据操作。
5. **兼容优先**：`LIGHTRAG_ENTERPRISE_AUTH_ENABLED=false` 时保持现有部署行为。
6. **审计优先**：所有安全敏感操作必须写 audit event。
7. **不保存明文密码/API Key**：数据库仅保存 password hash / API key hash。
8. **权限与 workspace 隔离互补**：workspace 继续负责数据隔离；RBAC 负责访问授权。

## 5. 配置项设计

### 5.1 企业模式开关

```env
# 默认 false。false 时保持现有 AUTH_ACCOUNTS / LIGHTRAG_API_KEY 行为。
LIGHTRAG_ENTERPRISE_AUTH_ENABLED=true
```

开启后：

- 禁止 guest token 访问受保护 API。
- `/kbs/...` route 必须使用 principal + RBAC 检查。
- 全局 `LIGHTRAG_API_KEY` 不再默认拥有所有 KB 权限；如需兼容，必须显式开启 legacy 策略。

### 5.2 超级管理员 bootstrap

推荐生产配置：

```env
LIGHTRAG_SUPER_ADMIN_USERNAME=admin
LIGHTRAG_SUPER_ADMIN_PASSWORD_HASH={bcrypt}$2b$12$replace-with-generated-hash
```

开发/首次引导可选：

```env
# 仅允许在非生产或显式允许明文 bootstrap 时使用。
LIGHTRAG_SUPER_ADMIN_PASSWORD=change-me-immediately
```

安全约束：

- 生产环境优先使用 `LIGHTRAG_SUPER_ADMIN_PASSWORD_HASH`。
- 若只提供明文 `LIGHTRAG_SUPER_ADMIN_PASSWORD`，启动时应发出高危告警；生产模式可直接拒绝启动。
- 首次启动创建超级管理员后，建议运维移除明文密码并改用 hash。
- 超级管理员账号禁用/删除必须受保护：不能删除最后一个 active super admin。

### 5.3 注册开关默认值

```env
# 仅作为首次初始化 system setting 的默认值；运行时以数据库中的 system_settings 为准。
LIGHTRAG_USER_REGISTRATION_ENABLED=false

# 可选注册模式：disabled / open / invite_only / admin_approval
LIGHTRAG_USER_REGISTRATION_MODE=disabled
```

运行时超级管理员可通过 API 修改注册策略，无需重启。

### 5.4 兼容全局 API Key

```env
# 默认 false。企业模式下不建议允许全局 API Key 绕过 RBAC。
LIGHTRAG_ENTERPRISE_LEGACY_API_KEY_SUPERADMIN=false
```

建议：

- 新企业部署不启用该兼容项。
- 老系统迁移期如必须使用全局 API Key，应设置短期过渡计划，并通过 audit 记录所有 API Key 操作。
- 正式企业模式应使用 service account API keys，每个 key 绑定明确权限和 KB 范围。

## 6. 核心概念模型

### 6.1 Principal

认证成功后，后端 route 应拿到明确的 `Principal`：

```python
@dataclass(frozen=True)
class Principal:
    subject_id: str
    username: str
    principal_type: Literal["user", "service_account", "guest"]
    system_role: Literal["super_admin", "user"]
    tenant_id: str | None
    auth_method: Literal["jwt", "api_key", "guest"]
    token_version: int
    is_active: bool
```

关键变化：

- 新 auth dependency 必须返回 `Principal`，不能只返回 `None`。
- route handler 不能信任请求体中的 `owner_id` / `tenant_id` / `created_by`。
- 服务端应从 `Principal` 推导 actor、tenant、created_by、updated_by。

### 6.2 系统角色

| 系统角色 | 说明 |
|---|---|
| `super_admin` | 平台超级管理员；可管理注册、用户、权限、所有 KB；唯一可删除 KB。 |
| `user` | 普通用户；权限由全局 capability 与 KB ACL 决定。 |

### 6.3 全局 capability

普通用户的全局能力建议拆成显式布尔/枚举：

| Capability | 说明 |
|---|---|
| `can_create_kb` | 是否允许创建新 KB。 |
| `can_use_bypass_query` | 是否允许使用 `mode="bypass"`。默认 false。 |
| `can_create_service_api_key` | 是否允许创建自己的 API Key。默认 false。 |
| `max_kbs` | 用户最多可拥有/创建 KB 数量。 |
| `max_concurrent_jobs` | 用户可发起的并发任务数。 |

### 6.4 KB 角色

| KB 角色 | 权限范围 |
|---|---|
| `kb_owner` | KB 业务 owner；可管理 KB metadata、ACL、配置、文档、查询、图谱，但不能删除 KB。 |
| `kb_admin` | 可管理配置、文档、任务、图谱和查询；可管理非 owner 成员。 |
| `kb_editor` | 可上传/替换/删除文档、parse/build/reindex、取消/重试相关 job、查询。 |
| `kb_viewer` | 可查看 KB、查询、查看图谱、查看 job 状态、下载允许的 artifacts。 |
| `none` | 无访问权限。 |

删除 KB 的权限不放在 KB 角色内，统一由 `super_admin` 控制。

| 字段 | 说明 |

| 字段 | 说明 |

### 8.7 audit_events

| 字段 | 说明 |
|---|---|
| `id` | 事件 ID。 |
| `actor_id` | 操作者。 |
| `actor_type` | user / service_account / system。 |
| `tenant_id` | 租户。 |

| `metadata` | 脱敏后的差异、job_id 等。 |
| `created_at` | 时间。 |

审计日志必须 append-only，普通管理员不可修改或删除。

## 9. API 设计

### 9.1 认证与当前用户

| 方法 | 路径 | 说明 | 权限 |
|---|---|---|---|
| `POST` | `/login` | 兼容现有登录，改为查 users 表。 | public |
| `POST` | `/auth/register` | 注册新用户，受注册开关控制。 | public when enabled |
| `GET` | `/auth/me` | 当前用户信息、全局 capability、可访问 KB 摘要。 | authenticated |
| `POST` | `/auth/change-password` | 修改自己的密码。 | authenticated |
| `POST` | `/auth/logout` | 可选：撤销当前 token/session。 | authenticated |

注册行为：

- `user_registration_enabled=false`：返回 403，错误码 `registration_disabled`。
- `mode=open`：创建用户，状态由 `default_new_user_status` 决定。
- `mode=admin_approval`：新用户为 `pending`，需超级管理员启用。
- `mode=invite_only`：必须携带有效 invitation token。

### 9.2 超级管理员设置

| 方法 | 路径 | 说明 |
|---|---|---|
| `GET` | `/admin/settings/registration` | 查看注册策略。 |
| `PATCH` | `/admin/settings/registration` | 实时开启/关闭注册、设置注册模式。 |

示例：

```json
PATCH /admin/settings/registration
{
  "enabled": true,
  "mode": "admin_approval",
  "default_new_user_status": "pending",
  "default_can_create_kb": false
}
```

### 9.3 用户管理

| 方法 | 路径 | 说明 |
|---|---|---|

## 12. 安全细节

### 12.1 密码安全

- 生产仅接受 bcrypt/argon2id hash。
- 明文 `.env` 密码只允许 bootstrap，并应有高危告警。
- 禁止将密码写入日志、audit metadata 或错误响应。

### 12.2 JWT 安全

- 企业模式强制非默认 `TOKEN_SECRET`。
- JWT payload 包含 `sub=user_id`、`username`、`system_role`、`token_version`。
- 每次请求校验用户状态和 `token_version`，防止禁用用户继续使用未过期 token。
- 禁用用户、重置密码、撤销所有会话时递增 `token_version`。

### 12.3 API Key 安全

- 明文 key 只在创建时返回一次。
- DB 只存 hash 和 key prefix。
- 每个 key 必须绑定 principal 与 scope。
- enterprise mode 默认不允许全局 `LIGHTRAG_API_KEY` 绕过 RBAC。

### 12.4 注册安全

- 注册默认 disabled。
- 登录/注册接口需要限流和失败锁定。
- `admin_approval` 模式下，用户需超级管理员启用后才能登录或访问 KB。

### 12.5 审计脱敏

审计日志不能保存：

- 密码、token、API Key 明文。
- 完整上传文档内容。
- 完整 query 文本和 LLM response，除非部署显式开启合规审计模式。

建议保存：

- query hash、前 N 字符摘要、token 数量、KB id、mode、耗时、结果状态。

### 15.1 默认兼容模式

## 16. 分阶段实施计划

### Phase 6A：基础用户与超级管理员

- 新增 users、system_settings、audit_events 最小 schema。
- 新增 super admin bootstrap。
- `/login` 改为查 users 表；保留兼容路径。
- 新增 `/auth/me`。
- 企业模式禁用 guest。

验收：

- `.env` 超级管理员首次启动可登录。
- 禁用超级管理员以外用户后 token 立即失效。
- 不能删除最后一个 super admin。

### Phase 6B：注册控制

- 新增 `/auth/register`。
- 新增 `/admin/settings/registration`。
- 注册开关持久化并实时生效。
- 支持 disabled/open/admin_approval，invite_only 可后续。

验收：

- 注册关闭时返回 403。
- 超级管理员打开注册后无需重启即可注册。
- 新用户默认无 KB 权限、不可创建 KB。

### Phase 6C：KB ACL 与 route 权限

- 新增 kb_acl。
- 新增 `AuthorizationService`。
- 替换 `/kbs/...` routers 的 auth dependency，传入 `Principal`。
- 强制 `DELETE /kbs/{kb_id}` super-admin-only。
- 强制 `POST /kbs` 检查 `can_create_kb`。
- `GET /kbs` 只返回授权 KB。

验收：

- 用户 A 无法访问用户 B 的 KB。
- 无 `can_create_kb` 用户不能创建 KB。
- `kb_viewer` 不能上传/删除文档。
- 只有 super admin 可以 soft/hard delete KB。

### Phase 6D：用户权限管理 API

- `/admin/users` CRUD。
- `/admin/users/{id}/kb-access:batch-set`。
- `/admin/kbs/{kb_id}/acl`。
- 前端管理台接入。

验收：

- 超级管理员可配置用户可使用哪些 KB。
- 权限变更实时生效。
- 被移除 KB ACL 的用户下次请求立即 403。

### Phase 6E：审计、API Key、限流配额

- 新增 audit event 写入。
- 新增 scoped service API keys。
- 新增登录/注册限流。
- 新增基础 quota checks。

验收：

- 权限拒绝、KB 删除、用户禁用、ACL 变更均有 audit event。
- scoped API key 不能访问未授权 KB。
- 超过并发 jobs/上传/query 限制时返回明确错误码。

### Phase 6F：legacy route 收口与生产演练

- 企业模式默认禁用或 super-admin-gate legacy global routes。
- 补充真实后端集成测试。
- 完成生产 rollout/rollback 文档。

验收：

- `/documents`、`/query`、`/graph` 不能绕过 KB ACL。
- 全外部后端演练通过。

## 18. 兼容性与风险

### 18.1 兼容策略

- 默认不启用企业模式，老部署不受影响。
- 企业模式启用后必须配置超级管理员。
- `AUTH_ACCOUNTS` 可作为迁移来源，但不再作为完整账户系统。
- `LIGHTRAG_API_KEY` 在企业模式下默认不作为 super admin。

### 18.2 主要风险

| 风险 | 缓解 |
|---|---|
| legacy route 绕过 KB ACL | 企业模式默认禁用或 super-admin-gate global routes。 |
| token 过期前权限仍有效 | token_version/session_epoch 每次请求校验。 |
| 请求体伪造 owner/tenant | 服务端从 Principal 写入 actor 字段。 |
| 注册被滥用 | 默认 disabled、限流、admin approval。 |
| 全局 API Key 过大权限 | scoped service API keys 替代。 |
| 审计泄露敏感内容 | 严格脱敏与字段白名单。 |

## 20. 推荐优先级

1. **P0：超级管理员 + Principal + super-admin-only KB delete**
   - 先堵住最高风险 destructive 操作。

2. **P1：注册开关 + 用户表 + KB ACL**
   - 满足核心用户管理诉求。

3. **P2：全 `/kbs/...` route RBAC 覆盖**
   - 防止读写绕过。

4. **P3：audit + scoped API keys + bypass gate**
   - 提升企业可审计与可控性。

5. **P4：quota/rate-limit/metrics/legacy route 收口**
   - 完成生产治理闭环。

## 21. 关键实现提示

1. 不要只把 `role` 塞进 JWT 就结束；必须每次请求查用户状态和权限版本。
2. 不要让 `X-API-Key` 在企业模式下天然拥有所有 KB 权限。
3. 不要继续使用 `dependencies=[Depends(combined_auth)]` 作为 KB route 的唯一保护；handler 必须拿到 `Principal`。
4. 不要相信请求体里的 `owner_id` / `tenant_id` / `created_by`。
5. 删除 KB、硬删除 KB、注册开关、授予权限必须写 audit。
6. 前端隐藏按钮只是 UX；安全必须由后端返回 403 保证。
